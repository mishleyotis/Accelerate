Brief overview

This brief is the single visual and interaction authority for the DMA Visualizer. It translates the product requirements (PRD v3), technical architecture (TRD v4), and user journeys (App Flow v3) into a complete, implementable design system. Every page, component, colour, type style, and interaction is specified here. Engineers should be able to build any screen by combining the patterns in this document without making visual decisions.

Three non-negotiable rules

1 — DM Sans only

Every text element uses DM Sans in one of five weights (200 / 300 / 400 / 500 / 600). No system fonts, no fallback fonts, no exceptions. This matches the Zennify slide brand exactly.

2 — Sentence case for every heading

"Maturity heatmap" not "Maturity Heatmap." This applies to all H1 through H4. Eyebrow text and maturity-level labels are the only ALL-CAPS exceptions.

3 — Zennify palette only

Every colour must be from the 57-colour Tier 1 palette. Generic red (#DC2626), generic green (#16A34A), generic yellow (#EAB308), and generic purple (#7C3AED) are forbidden. The 11 functional colours in §04 are the only colours used for status, error, and success states.

Logo prohibitions

Do

Keep the chevron and wordmark together when both are present (no orphan wordmark). Maintain minimum 8px clear space around any logo element.

Don't

Never recolour the chevron outside the teal/white pair. Never stretch or rotate the logo. Never apply drop shadows or glow effects. Never place the logo inside a card or content area — only in nav, footer, or page-level chrome.

Do

Use the chevron alone in compact UI (sidebar collapsed state, mobile top bar, favicons, toast notifications). The chevron is recognisable at sizes down to 16×16px.

Don't

Never use the chevron below 16×16px. Never combine the Zennify logo with another product mark to create a sub-brand (no "DMA Visualizer" wordmark exists by design).

The DMA Visualizer has no product-specific logo by design. It is a Zennify internal tool. The product name appears as plain DM Sans text below the wordmark in the sidebar header ("DMA Visualizer") at 11pt #8094C0 (purple/periwinkle). This prevents creation of an unauthorised sub-brand and keeps the parent identity dominant.

Section 02 · Foundation

Brand voice & microcopy

Every word in the app has a voice. The DMA Visualizer adopts Zennify's brand voice as defined in the design system: confident, specific, active. Insights are framed, not labelled. Challenges are described as opportunities. Numbers replace adjectives. This section is the contract for all microcopy: error messages, empty states, button labels, tooltips, and toast notifications.

Five voice principles applied to the app

1 — Confident, specific, active
Make claims backed by data. Never hedge.

Avoid: "There may be some thin evidence" → Use: "43 subcaps have evidence_count < 3"
2 — Client is the hero
In customer-facing surfaces (scorecard export, customer view), the institution is the protagonist. Internal views can be more direct.

Customer: "Farm Credit East scores 2.8 across digital maturity."
Internal: "FCE is at M2 building. Evidence ceiling is M3."
3 — Opportunity framing
Describe future state positively. No deficit language in customer-facing copy.

Avoid: "Pain points" "Weakness" "Lags" "Failure"
Use: "Areas of focus" "Room to grow" "Positioned to accelerate" "Opportunity"
4 — Word economy
Every word earns its place. Numbers beat adjectives.

Avoid: "There are a number of opportunities to consider"
Use: "4 platform opportunities"

Section 03 · Foundation

10 design principles

These principles are the resolution mechanism for every design conflict. When two options seem reasonable, the one that better expresses these principles wins. They derive from the Zennify brand voice, the UX principles in App Flow v3, and the operational reality of the DMA workflow.

1 — Evidence is one click away
Every scored claim, recommendation, and insight card surfaces its supporting evidence in a single click. The evidence drawer is the universal "show me why" mechanism. If a user has to navigate or scroll to find evidence, the design is wrong.
2 — Partial data beats no data
When a Phase 1 run is between batches, show what is available. When a Phase 0 entity has NULL fields, show NULL with context rather than hiding the entity. The user benefits from incomplete information more than from waiting for completeness.
3 — Deep links restore exact state
A URL captures every meaningful state — selected run, open drawer, open evidence item, audience mode, heatmap mode, filter set. Sharing a URL re-creates exactly what the sender was looking at. No "you'll need to navigate to..."
4 — Intelligence is additive, never required
Gemini surfaces enhance the UI. They do not gate it. If Gemini is unavailable, slow, or rate-limited, the 6 dashboards remain fully functional. The Intelligence Panel uses muted styling for failures — never alarming red.
5 — Role shapes hierarchy, not access alone
An AE landing on a client page sees a different information hierarchy than an Analyst lands on. Same data, different prioritisation. The AE sees the Opportunity Surface Score first. The Analyst sees the open alert count first.
6 — Provenance is always visible
Every assessment has a data source badge (DRIVE PARSE or PROJECT API). Every claim has an E-ID. Every score has an evidence count. The user can always answer "where did this come from?" without leaving the page.
7 — Staleness is a first-class signal
Freshness indicators are present on every entity card and client page header. Stale data is greyed-down but not hidden. Users seeing a 12-month-old assessment know what they're looking at without having to ask.
8 — Customer View is explicit and persistent
When Customer View is active, an amber banner cannot be dismissed. It is always visible at the top of the content area. This prevents the worst-case scenario: an AE accidentally screen-sharing internal-only fields during a client meeting.
9 — No dead ends
Every error state has a recovery action. Every empty state has a CTA or a clear "next step." Every failed search has filter-clear options. The user can never reach a state where the only option is to refresh the browser.
10 — Drive parse and API runs are equal citizens
A Phase 0 (DRIVE PARSE) entity is a fully-supported, first-class record. It is not "incomplete" or "preview." It appears in every list, every filter, every export. The DRIVE PARSE badge communicates provenance, not inferiority.

Section 06 · Visual foundation

Iconography

The app uses a curated icon set from the Zennify icon library (750 icons total) plus a small set of UI-utility icons (chevrons, close, search). Every icon is monochrome. Every icon is filled or outlined — never both styles in one screen. No emoji are used anywhere in the app interface.

Why no emoji

Emoji render differently on every OS and browser. They cannot be coloured to match the brand. They break visual rhythm in dense data UI. They make the app look casual when the user needs to perceive it as authoritative. Every place where v2 used an emoji (disk, lock, lightning, robot, cloud, warning) has been replaced with a styled DM Mono text label or a vector icon.

Button composition rules

Do

Microcopy guidelines

Microcopy is the single biggest lever on perceived product quality. This section is the complete reference for every type of microcopy in the app: errors, success messages, button labels, empty states, tooltips, and confirmation prompts.

Core rules — applied everywhere

  1. Sentence case for everything except eyebrow text and badges. "Save note" not "Save Note." "ACTIVATING" only in maturity labels and status badges.
