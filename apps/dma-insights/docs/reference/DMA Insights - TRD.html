Technical Requirements Document v3.0

How to read this document + Stack decisions

This document specifies every technical detail of the DMA Visualizer Web App — a Google Cloud-hosted platform that turns Zennify Digital Maturity Assessment outputs into an intelligent, real-time tool for Senior Account Executives. Every section is standalone: you do not need to have read a previous version.

If you are new to this system, start here. The DMA Visualizer does three things: (1) it collects DMA assessment results from Google Drive or a direct API post, (2) it lets you explore those results visually via a maturity heatmap and insight cards, and (3) it uses Google Vertex AI's Gemini models to synthesise findings into plain-English narratives and talking points — so an SAE can walk into a client meeting prepared without reading a 40-page report.

Technology stack decisions

Every choice below has a specific rationale tied to the DMA project's existing constraints. The DMA project runs in Python, lives in Google Drive, and is already hosted on GCP. Every technology decision reinforces those constraints — no new vendors, no cross-cloud complexity, no separate billing accounts.

Section 02

System architecture

Four Google Cloud Run containers work together to serve the app. One database, one cache, and one storage bucket. The Vertex AI API is called from the intelligence container — no separate AI infrastructure needed.

Plain English: how the four services divide their work. The frontend is what SAEs see in their browser — the heatmap, insight cards, intelligence panel. The api service handles all data requests from the frontend — reading scores, returning evidence, writing annotations. The intelligence service talks to Gemini on the api's behalf — it assembles context from the database, calls Vertex AI, validates the response, and streams tokens back. The worker is a background job that runs every 6 hours to crawl Google Drive for new DMA artifacts, parse them, and load them into the database.

How services authenticate to each other

Every call between Cloud Run services uses Google's built-in service-to-service OIDC tokens. This means no API keys are passed between internal services — Google Cloud verifies the caller's identity using the Cloud Run service account. The only exception is the ingest endpoint, which accepts a static API key from the Claude DMA Project running externally.

Complete request flow — Phase 1 ingest (how data enters the app)

1
DMA Project finishes an assessment (Batch 6)
The Claude DMA Project completes scoring for a client (e.g., Farm Credit East). The script scripts/post_to_app.py assembles all results into a structured JSON file called app_payload_v1.json and sends an HTTP POST to the ingest endpoint.
2
api service validates the payload
FastAPI receives the POST at /api/v1/ingest/assessment. Pydantic v2 validates every field — subcap count must match the expected range for the sub-vertical (e.g., Credit Union = 835–870 rows), scores must be 1.0–5.0, evidence_ids must match evidence items present in the payload. If validation fails, nothing is written — a 422 error with field-level details is returned.
3
Database write (single transaction)
All ~851 subcap score rows, evidence items, insight cards, tech stack entries, and recommendations are written in a single PostgreSQL transaction. Either everything succeeds or nothing is written — no partial ingests. If the same run_id is sent twice, the second call returns HTTP 200 with the existing receipt (idempotent).
4
5 async tasks run in the background
After the transaction commits, 5 background tasks run in parallel without blocking the HTTP response: (1) Thin evidence detection — flags subcaps with fewer than 3 evidence items. (2) Drive feedback write — generates 5 feedback JSON files and writes them to the entity's Drive folder. (3) Embedding ingest — calls text-embedding-004 to embed all evidence items into pgvector. (4) Platform fit scoring — computes Opportunity Surface Score per platform. (5) Intelligence cache warming — pre-generates 5 Gemini surfaces so the SAE sees instant results.
5
SSE broadcast to connected browsers
A message is published to Redis channel ingest:{entity_id}. Any browser currently viewing this entity's dashboard receives a real-time notification: "New assessment run available — Farm Credit East, Overall 2.8/5.0, 43 thin evidence alerts." The page updates without a refresh.
6
201 receipt returned to DMA Project
The ingest_receipt.json response includes: run_id, entity_id, status=ACTIVE, subcap_count, thin_evidence_count, alerts_generated, and the Drive path where feedback files were written. The DMA Project logs this receipt for audit.

Complete request flow — SAE intelligence drill-down

1
SAE clicks a subcap cell on the heatmap
The SAE is looking at Farm Credit East's P2 heatmap. They click P2C3.2.4 "Customer Journey Analytics" — a cell scored 2.0 in deep orange. The Intelligence Panel on the right immediately checks whether a cached narrative exists for this subcap (GET /intelligence/cache-status). If cached: response appears in under 50ms. If not: loading indicator shows while Gemini is called.
2
frontend sends request to api → api routes to intelligence service
POST /intelligence/subcap-narrative with body: {run_id, subcap_id: "P2C3.2.4", context_level: "QUICK"}. The api service proxies this to the intelligence service via an internal Cloud Run HTTPS call.
3
Intelligence service builds the context package
The Context Builder queries the database for: the subcap's score and rationale, all evidence items for this subcap with tier/recency/facts, maturity descriptors for levels M2 (current) and M3 (next target) from Tab 6, Agentforce agents anchored to this subcap (from Tab 8), cross-pillar stories mentioning this subcap (from Tab 14), peer scores for P2C3.2.4, and the top 3 productized offerings that cover this subcap (from Tab 12). This assembles ~10,000 tokens of grounded context.
4
Gemini call with structured prompt
The subcap_narrative_v3 Jinja2 template is loaded from GCS and populated with the context package. The prompt instructs Gemini to produce: current state diagnosis, gap to M3, peer comparison, platform opportunity (named L3 + L4 feature), one Agentforce agent recommendation (must be from the Tab 8 registry), and 3 conversation starters under 25 words each. Temperature is 0.3 — low randomness for consistent analytical output.
5
Anti-hallucination check + streaming to browser
As each token arrives from Gemini, the validator checks any agent ID pattern (AF-xxx, FM-AGENT-*) against the 470-agent registry from Tab 8. Valid tokens stream straight to the browser. An unrecognised agent ID triggers a hallucination_flag SSE event before that segment — the SAE sees a yellow warning border around the flagged text.
6
Cache write and SAE reads the narrative
When streaming completes, the full response is stored in Redis (4h TTL) and the intelligence_cache database table (permanent, auditable). The SAE now has a 400-word, evidence-grounded narrative with 3 ready-to-use conversation starters for this specific subcap at this specific client.
Section 03

Database schema

22 PostgreSQL tables across 5 groups. The schema is designed around three concerns: storing DMA assessment data accurately, making heatmap queries fast, and giving Gemini the structured catalog context it needs to generate grounded intelligence.

Plain English: why 22 tables? The 4 largest tables hold the actual DMA data: entities (one row per client institution), assessment_runs (one row per DMA execution), subcap_scores (~851 rows per run — the heatmap cells), and evidence_items (~300 rows per run). The remaining 18 tables hold the V7.0 catalog (for intelligence context), the intelligence cache (for Gemini responses), and admin/operations data (import jobs, user accounts).

Group 1 — Core assessment data

Foreign key rule: all foreign key constraints are set to ON DELETE RESTRICT. This means you cannot accidentally delete an entity if it still has assessment runs, or delete a run if it still has subcap scores. Data is archived, not deleted.

Section 04 · Phase 0

Drive ingestion service

Phase 0 is the app's "self-service" bootstrap mode. Without any changes to the DMA project, the app crawls the Google Drive folder where DMA artifacts live, parses the documents it finds, and loads the data into the database. This is how the app can be pre-populated with all historical DMA runs from day one.

Plain English: what the worker does every 6 hours. It asks Google Drive "what files changed since I last looked?" It downloads those files, figures out which client institution they belong to, parses the scores and evidence out of the documents, deduplicates if the same entity has multiple versions, and loads everything into the database. Entities that look like test cases (PropTech companies, files named "template", etc.) are automatically excluded. After loading, it embeds all evidence items into the vector database so SAEs can do semantic searches.

Worker execution sequence

1
Metadata crawl (no file content downloaded yet)
The worker calls the Drive API to list files in the DMA Assets folder (ID: 1O0JyNGKRUtz7HqiIAvehIwU-texDcT_0). In DELTA mode, it only requests files modified since last_crawl_at (stored in system_config). In FULL mode, it requests all files. Each file's name, MIME type, owner, parent folder, and modification time are fetched but the actual document content is not yet downloaded. This metadata-first approach lets the worker classify and filter most files without paying Drive API quota for content fetches.
2
Test case exclusion (rules R01–R06)
Six rules automatically exclude files from the import. Any file triggering R01–R03 is immediately excluded. Files triggering R04–R06 are placed in the REVIEW queue for a human admin to decide.
3
Entity inference
For each surviving file, the worker tries to figure out which client institution the file belongs to using a 4-signal cascade (Assessment ID → document header → filename tokens → parent folder name). Confidence scores determine whether the match is accepted automatically or sent to the REVIEW queue.
4
Deduplication winner selection
If multiple artifacts for the same entity and same artifact type exist (e.g., two versions of a Assessment Report), the 4-rule deduplication logic picks the authoritative winner. The non-winners are logged in the audit trail but not imported.
5
Content fetch + parsing (max 5 concurrent)
The winner files are downloaded and parsed. A semaphore limits concurrent downloads to 5 to avoid Drive API rate limits. DOCX files are parsed by the AssessmentReportParser or ClientProfileParser. XLSX files are parsed by the WorkbookParser. JSON files matching the app_payload schema are passed through directly.
6
Synthetic payload assembly
For each entity, all its parsed artifacts are merged into a single SyntheticPayload object using a priority hierarchy (app_payload_v1.json wins over workbook which wins over report which wins over research report). The result is structurally identical to a Phase 1 payload — it goes through the same Pydantic validation and the same database upsert function.
7
Post-ingest: embed + platform score + intelligence bootstrap
Same 5 async tasks as Phase 1: thin evidence detection, embedding ingest, platform fit scoring, intelligence cache warming, and audit log update. The last step updates last_crawl_at in system_config.

Test case exclusion rules (R01–R06)

Important: Test case exclusion protects the entity directory from being polluted with internal Zennify test runs, template files, and non-FSI entities. The specimen case is "Nyumba Zetu" — a PropTech company used in internal DMA testing that triggers R02 (no Assessment ID) and R03 (non-FSI entity category). All 6 rules are checked before any content is downloaded.

Entity inference cascade

The inference system tries 4 signals in order. The first one that produces a confident match is used. Confidence below 0.70 = UNRESOLVED queue for human admin review.

Deduplication winner selection rules

When multiple files resolve to the same entity + artifact type combination, these 4 rules run in priority order. The first rule that differentiates the candidates picks the winner.

  1. _FINAL suffix wins. If one file contains "_FINAL" in the name and others do not, the _FINAL file wins unconditionally. This reflects the DMA project's naming convention for completed deliverables.
  2. Assessment ID date component wins. The file with the most recent date in its Assessment ID (YYYYMMDD) wins. e.g., DMA-ASM-FCE-20260601-0001 beats DMA-ASM-FCE-20260312-0001.
  3. Drive modification time wins. If Assessment IDs are identical (or absent in both), the file with the most recent modifiedTime from the Drive API wins.
  4. DMA Agent owner wins. If all other signals are equal, a file owned by the dma@zennify.com service account beats a file owned by a named user (e.g., sam@zennify.com). The service account produces the canonical automated output.

Section 05 · Phase 0

Artifact parsing

The parsing layer converts DMA documents (DOCX reports, XLSX workbooks, JSON handoff files) into structured Python objects. These objects are then merged and written to the database. The parser is deliberately forgiving — partial parses are better than complete failures.

Plain English: what "parsing" means here. A DMA Assessment Report is a Word document. To get the scores out of it, we need to search for text patterns like "Overall Score: 2.8" or table headers like "Pillar | Score | Peer Median". The parser does this systematically, using known section header anchors from the DMA templates. A XLSX workbook is easier — we read the exact cells in the 11 pre-defined column positions. JSON files (research_handoff.json, app_payload_v1.json) are already structured — we just validate and pass them through.

Artifact type priority hierarchy

When multiple file types exist for the same entity, the synthetic payload assembly merges them in this order. Higher-priority sources overwrite lower-priority sources for the same field — they never overwrite with NULL.

Section 06 · Phase 1

Ingest API, payload schema & batch-by-batch flow

Claude does not wait until the end of an assessment to post data. It sends a structured payload to the app after every completed batch, building a living run record incrementally. By the time the final batch completes, the app already has partial data visible to the team and the full payload is a final merge, not a first write.

Plain English: why batch-by-batch matters. A DMA engagement takes hours to complete. If Claude only posted at the end, the app would have nothing useful for hours after a run starts. Section 07 · Phase 1

Feedback loop implementation

After every ingest (Phase 1 or Phase 0), the app writes structured feedback files back to the entity's Google Drive folder. The DMA project reads these files at the start of Batch 1 (the next time a DMA is run for the same entity) and uses them to focus the research and avoid known weaknesses.

Plain English: the app talks back to the DMA project via Drive. When the app detects thin evidence (fewer than 3 items for a sub-capability), it writes a feedback file to Drive saying "P2C3.2.4 only has 1 evidence item and proxy searches were never attempted — prioritise this." The next time an analyst runs the DMA for this entity, the DMA project reads that file at the start and adds extra research queries for the flagged sub-capabilities. It's a quality improvement loop.

Performance strategy

851 SVG elements is within SVG's comfortable range — no canvas required. The primary performance concern is the initial render of the subcap heatmap. These optimisations keep it fast:

  • Data pre-fetched at route load: the heatmap data (851 rows) is fetched as the entity page loads, not when the user clicks the heatmap tab. By the time they click, data is already in the React Query cache.
  • Virtual scroll for the full-subcap list: when displaying all 851 subcaps in a flat list view, @tanstack/react-virtual renders only the cells currently in the viewport.
  • D3 transitions capped at 200ms: zoom transitions use D3's transition().duration(200) — short enough to feel snappy but long enough to be readable.
  • Read replica for all heatmap queries: the heatmap endpoint always queries the PostgreSQL read replica. Primary database is reserved for writes (ingest, annotations).
  • 30-second Redis cache per run: once the heatmap data is loaded for a run, it stays in Redis for 30 seconds. Rapid page navigation (switching between pillar tabs) hits the cache, not the database.

Anti-hallucination validator

This is the most important safety mechanism in the intelligence layer. It runs on every Gemini response token by token as the stream arrives. Its job is to catch cases where Gemini invents Agentforce agent names or platform construct names that do not exist in the V7.0 catalog.

# intelligence/validators/anti_hallucination.py import re AGENT_ID_PATTERN = re.compile(r"(AF-\d+|FM-AGENT-[A-Z0-9-]+)") class AntiHallucinationValidator: def __init__(self, agent_registry: set[str]): # Set of valid agent_ids from the agentforce_agents table # e.g., {"AF-001", "AF-002", "FM-AGENT-DATA-QUALITY-STEWARD", ...} self.registry = agent_registry self.buffer = "" self.flags: list[dict] = [] def process_chunk(self, chunk: str) -> tuple[str, list[dict]]: # Buffer chunks to catch agent IDs that span two streaming packets self.buffer += chunk flags = [] for match in AGENT_ID_PATTERN.finditer(self.buffer): agent_id = match.group(0) if agent_id not in self.registry: flags.append({ "agent_id": agent_id, "text_segment": self.buffer[max(0, match.start()-30):match.end()+30], "severity": "HALLUCINATION" }) # Flag emitted as a separate SSE event before the offending text # Frontend renders that text segment with a yellow warning border # Flush buffer once agent ID patterns cannot span the next chunk safe_prefix = self.buffer[:-40] # keep last 40 chars as overlap self.buffer = self.buffer[-40:] self.flags.extend(flags) return safe_prefix, flags

Synthesis engine

The synthesis engine runs inside the intelligence Cloud Run service. It has three operating modes depending on what the surface needs: streaming narrative for SAE-facing surfaces, structured JSON for machine-readable outputs that the frontend renders as formatted cards, and semantic vector search for evidence retrieval.

Mode 1 — Streaming narrative

Authentication & authorisation

All app users must be @zennify.com Google accounts. Login uses Google OAuth 2.0 OIDC. The frontend issues a short-lived RS256 JWT for every API request. The ingest endpoint uses a separate static API key for the Claude DMA Project — it cannot use Google OAuth because it runs as an automated script, not a human user.

Plain English: how login works. An SAE visits the app URL. They click "Sign in with Google." Google shows its standard "Choose an account" screen. If the SAE selects their @zennify.com account, Google sends the app a confirmation (an OIDC id_token). The app verifies the email ends in @zennify.com, creates a session, and issues a JWT. Every subsequent API call includes that JWT in the Authorization header. The FastAPI backend validates the JWT signature using Google's public keys before processing any request.

Google OAuth 2.0 OIDC login flow (6 steps)

1
SAE visits the app and clicks "Sign in with Google"
NextAuth.js redirects the browser to Google's authorisation endpoint: https://accounts.google.com/o/oauth2/auth?client_id=...&redirect_uri=...&scope=openid email profile&response_type=code&hd=zennify.com. The hd=zennify.com parameter restricts the account picker to Google Workspace accounts in the zennify.com domain.
2
Google authenticates the user
The SAE selects their @zennify.com account and completes any 2FA required by the Zennify Google Workspace policy. The browser is redirected to the app's callback URL with a one-time authorization code.
3
Backend exchanges code for tokens
NextAuth.js calls Google's token endpoint server-side (from Next.js, not from the browser). Google returns an access_token, refresh_token, and an id_token (JWT containing the user's email, name, and Google sub identifier).
4
Domain validation + user record upsert
NextAuth.js verifies the id_token's signature using Google's JWKS endpoint. The email is checked to confirm it ends in @zennify.com. If the user is new, a record is created in the users table with role=AE. If they already exist, the existing role is preserved. The Google sub (stable unique user ID) is used as the lookup key — not the email, because emails can change.
5
App issues its own RS256 JWT
NextAuth.js generates an app-scoped JWT signed with an RS256 private key (stored in GCP Secret Manager). The JWT payload contains: sub (user's UUID from the app's users table), email, role (ADMIN|ANALYST|AE), iat (issued at), exp (expires in 1 hour). The corresponding public key is available for FastAPI to verify.
6
Every API request carries the JWT
The frontend stores the JWT in an HttpOnly cookie (not localStorage — prevents XSS theft). Every fetch to the API includes this cookie. FastAPI's JWT middleware validates the RS256 signature and expiry on every request. An expired JWT redirects to login. A valid JWT extracts the user's role to determine which fields to return in the response.
