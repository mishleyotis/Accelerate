Overview & design principles

This document maps every user journey, authentication gate, friction point, persistent storage event, and state transition in the DMA Visualizer. v3.0 adds full Phase 0 (Drive-based bootstrapping) flows and aligns all visual language with the Zennify design system v2.4.15.

Phase architecture — two operating modes

Phase 0 — Drive bootstrap
The app bootstraps from completed DMA artifacts already in Google Drive. No changes to the DMA project required. The app discovers, classifies, parses, and deduplicates files autonomously. Entities sourced from Drive are tagged data_source: DRIVE_PARSE. Phase 0 is never removed — it becomes the permanent "manual import" path.
Phase 1 — Claude Project API
The DMA project posts app_payload_v1.json directly to the app's ingest endpoint after each completed run. No Drive polling. No content parsing. Schema-validated JSON ingested directly. Entities updated via Phase 1 are tagged data_source: PROJECT_API. Phase 0 entities coexist and are not displaced.

10 core UX principles

1 — Deep links always work
Every meaningful state lives in the URL. /clients/abc/heatmap?subcap=P2C3.2.4&hm=value_chain restores that exact state including the open evidence drawer.
2 — Partial data is always better than none
Phase 0 Drive-parsed entities show immediately even with NULL fields. In-progress Phase 1 runs surface available data after each batch. The app never waits for a complete payload to display something useful.
3 — Intelligence Panel never blocks
The Gemini panel is strictly additive. All 6 dashboard clusters are fully functional without it. Gemini failure shows a soft advisory — not an error page.
4 — Customer View is explicit and reversible
An amber persistent banner appears whenever Customer View is active. Toggling is one click. The toggle is always visible in the top-right of client pages.
5 — No dead ends
Every error state has a recovery action. Every empty state explains why it is empty and what the next step is. The app never shows a blank screen without context.
6 — Role-based UX, not just access
The information hierarchy adapts to role. ANALYST sees alert count badges prominently. AE sees the Opportunity Surface Score and "Why now" signals first. Same data, different prioritisation.
7 — Staleness is always visible
Freshness indicators (green/amber/red) appear on every entity card and in the client top bar. Phase 0 entities show their data_source: DRIVE_PARSE badge so AEs know when data came from a parsed document vs a live API run.
8 — One click to the evidence
Every scored claim, recommendation, and insight card surfaces its evidence in one click. The evidence drawer slides in without navigating away.
9 — Run comparison is non-destructive
Viewing a superseded run never changes the active run view. An amber banner labels the non-active state. The diff includes Drive-parse vs Phase 1 structured comparisons.
10 — The app works when Gemini is down
The Intelligence Panel is optional. Gemini unavailability shows a soft "Analysis temporarily unavailable" advisory in the panel. No functionality outside the panel is affected.

Section 01 · Authentication

Authentication & session management

Every route is auth-gated except /login. All users must be @zennify.com Google accounts. The ingest endpoint uses a separate static Bearer key — not user JWT. Deep links are preserved through the login redirect.

AUTH gate

Any unauthenticated request to any route is redirected to /login?callbackUrl=...original-url.... After successful login the user returns exactly to where they were, including open drawers and URL params.

First visit — complete login flow

1
User navigates to the app URL AUTH
NextAuth.js middleware runs on every request. No valid session → immediate redirect to /login?callbackUrl=%2F. The login page is the only route accessible without authentication.
2
Login page — "Sign in with Google" only
Zennify logo, one button: "Sign in with Google." No username/password form. Message: "Access restricted to @zennify.com accounts." No other login method exists.
3
Google OAuth redirect with hd=zennify.com restriction UX
Redirected to accounts.google.com/...hd=zennify.com. The Google account picker appears. Friction: users with personal Gmail accounts selected in Chrome may accidentally pick the wrong account. Resolution: non-zennify selection returns to /login?error=OAuthAccountNotLinked with: "Only @zennify.com accounts are permitted. Please select your Zennify account." Retry button restarts the flow cleanly.
4
Google confirms → NextAuth receives the callback
Google redirects to /api/auth/callback/google?code=...&state=.... NextAuth exchanges the code for tokens server-side. Verifies id_token signature using Google's JWKS endpoint.
5
Domain validation + user record upsert DB
Confirms email ends in @zennify.com. Upserts user record: existing google_sub → return with existing role. New → create with default role AE. Roles are never changed automatically — only by ADMIN action. New user sees: "Your account has been created with the AE role. Contact an admin to request Analyst or Admin access."
6
RS256 JWT issued → HttpOnly session cookie set Cookie
NextAuth generates app-scoped JWT: user UUID, email, name, role, iat, exp (+1 hour). RS256 private key from Secret Manager. Stored as HttpOnly Secure SameSite=Strict cookie named dma-session. Unreadable by JavaScript.
7
Redirect to original URL URL
User redirected to callbackUrl from step 1 — or / if no callback. All subsequent navigation works without re-authenticating.

Role gate enforcement — two-layer model

Both layers must agree. The FastAPI backend strips or rejects requests based on the JWT role claim. The Next.js frontend hides UI elements based on session role. A user cannot access restricted data by manipulating the frontend — the backend enforces the same rules independently.

Design note

The thin-evidence indicator uses an orange dashed outline (#FE9732), not red. Red is reserved for below-benchmark indicators (#C25008). This distinction matters: thin evidence is a data quality signal, not an error state. Per PRD v3 §07 and design system color_system.md §DMA-Specific.

This section maps the complete 10-step import pipeline — from crawl trigger to database record — including entity inference, test case removal, and deduplication as specified in PRD v3 §09–§15.

PH0Target Drive folder: 1uvt3kh8vPIygFwUNfKQSol0m5OYj2O0P (DMA Assets). Flat structure with mixed naming conventions. Entity inference required for every file.

10-step import pipeline (PRD v3 §15)

1
Crawl trigger PH0

Section 24 · Phase 0

Phase 0 — Entity PENDING_REVIEW

When Drive inference creates a new entity that was not previously in the database, it starts with status PENDING_REVIEW. It is not shown in the entity directory until an ADMIN confirms the entity is a valid FSI institution. This prevents accidental import of misclassified non-clients.

Why this exists

Drive entity inference uses a confidence cascade. Files with confidence ≥ 0.7 are auto-matched. Files that create new entities are automatically flagged PENDING_REVIEW because the inference has not been confirmed by a human. An ADMIN must review the evidence before the entity appears in the directory.

PENDING_REVIEW entity lifecycle

1
Drive crawl creates a new entity from inference
An entity is inferred from a Drive file with confidence between 0.7 and 0.89 (Assessment ID found, or name extraction confirmed, but entity is new to the DB). Entity record created with review_status: PENDING_REVIEW. The entity's data is fully ingested into the DB — only its visibility is gated.
2
Admin notified SSE
Admin's sidebar shows a badge on the Admin nav item: "[N] entities pending review." The /admin page has a PENDING_REVIEW section with one card per entity: inferred name, inferred subvertical, confidence score, which rule produced the inference, and a link to the source Drive file.
3
Admin reviews inference evidence
Each PENDING_REVIEW card shows: the matching evidence (Assessment ID found, entity name extracted from header, filename tokens matched). Admin can view the first 2,000 characters of the source document inline. Confidence score and which cascade signal produced the match is shown with explanation.
4
Admin confirms or rejects DB
Confirm: Optional name correction, subvertical selection, and domain entry. Entity review_status → CONFIRMED. Entity immediately appears in the entity directory with the DRIVE PARSE badge.
Reject: Entity is marked EXCLUDED and will not appear again unless manually re-imported. Source file is logged in the import_audit table as R02 (non-resolvable).

Intelligence Panel soft failure design

AI failures must be soft

Intelligence Panel failures use neutral grey styling — never orange or below-benchmark red. The panel is additive; its failure must never alarm the user or suggest the main dashboard is broken. "Analysis temporarily unavailable" with a retry option is the correct pattern. All 6 dashboard clusters remain fully functional regardless of panel state.
