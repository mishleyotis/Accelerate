DMA Visualizer Web App

An interactive intelligence platform that transforms completed Digital Maturity Assessments into a living, queryable workspace. It stores, revises, and presents the full depth of every DMA run — from entity identity through subcapability-level evidence — and feeds quality signals back into the DMA execution engine to drive stronger reruns. It operates in two phases: Phase 0 bootstraps from existing Google Drive artifacts without requiring any changes to the DMA project; Phase 1 connects directly to the Claude Project API for structured, real-time payload delivery.

Core thesis

The DMA produces ~836 scored subcapabilities, hundreds of evidence items, insight cards, issue registers, peer benchmarks, financial trajectories, and platform opportunity maps. Less than 20% of this reaches an AE today. The Visualizer surfaces the other 80% — selectively, interactively, and without overwhelming the viewer. It does this without replacing the DMA engine; it extends it.

Scope

In scope — v1

  • Internal tool: Zennify AEs and delivery team
  • Phase 0: Drive crawl, classify, parse, and import existing artifacts
  • Phase 1: Direct Claude Project API ingest channel
  • Interactive heatmap (pillar → subcap drill-down)
  • Insight cards with evidence drill-down
  • Platform opportunity matrix (SF, DB, Tableau, Twilio, nCino)
  • Thin-evidence detection + feedback to DMA project
  • Version history and run-to-run diff
  • Lightweight scorecard and PDF export
  • Internal/customer view toggle

Out of scope — v1

  • Customer-facing portal
  • Real-time research or live scraping
  • Replacing the Claude DMA execution engine
  • Salesforce / CRM write-back
  • Octar console integration (v2 candidate)
  • Natural language chatbot query interface (v2)
  • Cost, ROI, or investment projections
  • Multi-tenant white-label deployment

Section 02

Problem statement

The DMA pipeline produces some of the richest institutional intelligence in Zennify's possession. It is being systematically underused. Four compounding failure points prevent it from reaching its audience.

The static artifact problem

Every completed DMA produces DOCX and XLSX files written to Google Drive. To access a specific finding, an AE opens a 40–80 page Word document, navigates manually, and interprets tables without context. The assessment report alone contains 12 structured sections — executive summary (SCQA format), trend analysis, issue register with timeline, four pillar deep-dives, benchmark comparison, gap prioritization, recommendations with root cause analysis, a transformation roadmap, data gaps, and a full evidence registry. None of this is searchable, filterable, or cross-referenceable in a static document.

The evidence depth problem

Each subcapability score is backed by evidence items with tier ratings, ERS scores, claim-type labels (FACT / INFERENCE / HYPOTHESIS / CEILING_ESTIMATE), source URLs, and verbatim excerpts. The insight cards from the Client Profile — each structured around WHAT / WHY / SO WHAT — contain the most commercially relevant analysis in the engagement. They sit as rows in a table on page 20 of a Word document that AEs rarely open.

The platform recommendation problem

Recommendations reference named platforms: Salesforce Agentforce, Databricks Mosaic AI, Tableau Next, Twilio Engage, nCino Workflow Engine, Salesforce Data Cloud. Each subcapability gap maps to L3 platforms with L4 features and use cases from the V7 capability catalog. Today this is prose in a recommendations section with no way to filter by platform, see all gaps a specific platform addresses, or understand platform fit relative to the client's full maturity profile.

The rerun quality problem

When a DMA is rerun the project has no memory of where the prior run was thin. Subcapabilities with fewer than three evidence items receive no special attention. Proxy searches that were not attempted are not flagged. The result is reruns that replicate the same evidence gaps, with no mechanism to improve coverage over time.

The version coherence problem

Multiple runs for the same entity accumulate in Drive with no comparison mechanism. An AE asking whether a client's P4 score improved must open two XLSX files and manually compare rows. No delta view, no signal of regression or improvement, no way to trace whether a prior recommendation was ever actioned.

Section 03

User personas

Three personas. Each has a distinct relationship to the assessment data and a distinct primary question. The app must serve all three without privileging any one view by default.

AE
Account Executive
Sales · Client-facing
Needs a fast ramp on an entity before a meeting. Looking for angles — what platform gaps exist, what the peer story is, what the "why now" trigger is, and what the one-page framing for a conversation looks like. Does not read the full DOCX.
Understand an entity's maturity posture in under 3 minutes
Identify the strongest platform opportunity and its evidence base
See how the entity compares to named peers in the same subvertical
Generate a clean export for a first call or follow-up
Know whether the assessment data is current
DL
Delivery lead
Internal · Pre-sales + post-sale
Works after the AE opens the door. Needs to go deeper — which subcapabilities are driving the score, what the "What We See / Why It Matters" narrative says for each pillar, what the transformation roadmap implies for scoping. Uses the app to prepare for discovery and to frame the solution design conversation.
Navigate pillar deep-dives without reading a Word document
Understand which issues are capping scores and by how much
Map gaps to specific platforms with L3/L4 feature detail from V7 catalog
Annotate insight cards with post-meeting context
Compare this entity's profile to similar completed engagements
AN
DMA Analyst
Internal · Assessment operations
Runs and manages DMA executions. Primary operator of the feedback loop between the app and the DMA engine. Needs to see which subcaps are thin on evidence, confirm which entities are due for a rerun, review version diffs after a refresh, and manage the quality health of the scoring database.
Review thin-evidence alerts and mark them for next rerun
Compare run N to run N−1: what changed, what regressed, what resolved
Monitor assessment health across all entities
Verify each recommendation traces to a named platform and evidence-backed gap
Schedule reruns for stale entities

Visibility model. All three personas see the same data by default. The internal/customer toggle controls which sections are safe to screen-share with a prospect. It hides fields tagged internal_only: true — evidence excerpts, raw rationales, ERS scores, issue severities, and event timelines. The toggle is a display-mode switch, not a separate data tier. Analysts always see everything regardless of mode.

For a selected capability cluster or value chain: current score → M3 target → M5, annotated with which platform enables each step-up. Vertical-specific — the curve shape varies by subvertical pillar weights. Exported from the heatmap view.

AEDelivery
Reframes the entire assessment through a platform lens. Instead of "how mature is this institution?" it asks "which platforms have the most evidence-backed business case here?" This is the primary commercial view before a platform-specific conversation.

Phased roadmap from Assessment Report §10: Phase (duration) → key recommendations → maturity target → success metrics. Linked to specific platform deployments. Each phase shows the maturity trajectory by period end.
Recommendation cards
Each REC-XX from the assessment: root cause with E-IDs, solution with named platform + Zennify offering, expected outcomes table. Filterable by platform and phase. Root cause E-IDs are clickable to the evidence drawer.
Conversation Starter Generator NEW
For a selected platform: 3–5 concise evidence-backed talking points for a first call. Entity-specific, peer-comparative, evidence-cited. Template-fill from stored assessment fields — not AI-generated. Copyable to clipboard.

Context & Timeline
Historical intelligence · "What has happened here and what does it signal?"
DeliveryAE
Surfaces the historical context layers: financial trajectory, digital evolution timeline, issue register with visual Gantt, regulatory standing, acquisition history, and sentiment overview. Flagged internal_only by default — team preparation, not client-facing.
Digital evolution timeline
Interactive horizontal timeline: each event is a node (Date, Initiative, Evidence ID, Capability Impact, Maturity Signal). Colour-coded by signal type: positive (teal), negative (orange), neutral (gray). "Why now" signals in Dashboard 1 are drawn from this timeline.
Issue register — Gantt view
Issue Timeline from Assessment Report §4 as a Gantt-style track. Each issue shown as a bar (start → resolution or open). Severity by colour (CRITICAL=red, MATERIAL=amber, MINOR=gray). Expanding any bar shows: type, description, capability impact, cap value, status.
Financial trajectory
5-year financial growth chart with CAGR annotation (from Client Profile §3.2). Trend classification (ACCELERATING / STABLE / DECLINING / VARIABLE). Context for budget conversations — an institution at 12% asset CAGR is in a different investment posture than one at −2%.
Regulatory standing
Primary regulator, license status, enforcement action history (or confirmed-clean from negative search results), additional jurisdictions. Enforcement actions that cap scores are linked to their issue records. Directly impacts deal complexity framing.
Sentiment overview
Employee sentiment (Glassdoor), customer sentiment (app store, complaint trends), and media sentiment distribution. From Client Profile §3.4. Sentiment data impacts P2 scoring caps — low customer sentiment caps customer experience subcapabilities at M3.
Acquisition history
M&A activity from Client Profile §4.4 as timeline events. Each acquisition: entity acquired, date, integration status, and technology fragmentation implication — explaining P4 fragmentation signals where applicable.

Assessment Health
Analyst workspace · "What is the quality of this data and what needs to be done?"
Analyst
The Analyst's primary workspace. Surfaces quality signals, thin evidence, safeguard gate statuses, and version diffs. Provides the controls that drive the feedback loop back to the DMA engine for stronger reruns.
Thin evidence alert dashboard
All subcaps with evidence_count < 3 or NO_EVIDENCE. Ranked by severity. Alert workflow: OPEN → IN_REVIEW → RESOLVED / WAIVED. Resolution triggers regeneration of thin_evidence_feedback.json and Drive write-back.
Version diff view
Side-by-side subcap score comparison between any two runs for the same entity. Delta cells colour-coded. Evidence count delta column. Score regressions >1.0 flagged. New/resolved alerts shown. Exportable as CSV.
Safeguard gate status
All 10 gates from the assessment (G01–G10) shown as PASS/FAIL with supporting evidence. FAIL gates are blockers shown in red. Must be resolved before the run is considered delivery-ready.
Cross-entity pattern finder NEW
Global view: for each category, distribution of scores across all entities in the same subvertical. Surfaces categories where ≥60% of a subvertical scores <2.5 — potential multi-account platform campaign. Filtered by subvertical.
Evidence age tracker NEW
Per subcap: publication date of most recent evidence item. Subcaps with newest evidence >18 months flagged as potentially stale. Entity-level: if >40% of subcaps are stale → entity marked for rerun in the freshness dashboard.
Assessment freshness dashboard
Global view across all entities: last run date, evidence age indicator, open alert count, whether a rerun is scheduled. Sortable by staleness. Primary triage tool for the Analyst deciding which entities to prioritise for a research refresh.

Platform Fit Score formula

// FitScore(Platform P, Entity E) FitScore = Σ priority_score(s) × gap_size(s) for all subcaps s where: score(s, E) < 3.0 // gap exists P ∈ l3_platforms(s) // platform addresses this subcap in V7 catalog tech_status(P, E) = ABSENT // platform not deployed — confirmed by Explorium confidence(s, E) ≠ LOW // evidence-backed gap, not speculative // priority_score uses the 6-factor formula from Assessment Report §8: priority = (0.25 × gap_size) + (0.20 × peer_comparison) + (0.15 × strategic_alignment) + (0.15 × implementation_complexity) + (0.15 × investment_efficiency) + (0.10 × stakeholder_readiness) // gap_size = 3.0 − score(s, E) for scores below 3.0. Threshold = M3 (Competing)

Section 10 · Phase 0

Folder traversal

The traversal algorithm crawls the target Drive folder and all sub-folders recursively, collecting all files. It treats the entire tree as a flat pool of candidate artifacts and classifies each one independently — no assumed folder structure.

Target folder: drive.google.com/drive/folders/1uvt3kh8vPIygFwUNfKQSol0m5OYj2O0P. Confirmed structure from Drive search: artifacts live largely flat in DMA Assets. Files owned by dma@zennify.com (programmatic) or named users (manual). No enforced per-client sub-folder structure — inference required.

Traversal sequence

1
Root folder metadata crawl
List all files in the target folder ID. Collect: Drive file ID, MIME type, name, modifiedTime, createdTime, owner email, parent folder ID. No content fetch at this stage — metadata only. Paginate via pageToken (100 files per call).
2
Recursive sub-folder expansion
For every item where mimeType = application/vnd.google-apps.folder: recurse. Track the folder path as an entity inference signal. Max depth 6. Sub-folder names that match known clients (e.g., "Farm Credit East") are logged as strong entity signals even if the file ultimately has a different name.
3
MIME type filter
Retain: Google Docs, Google Sheets, Google Slides, DOCX, XLSX, PPTX, JSON, and ZIP. All other MIME types discarded silently (logged at DEBUG). This is the first reduction of the candidate pool.
4
Delta filtering
For scheduled crawls: retain only files with modifiedTime > last_crawl_at. Full rescan available via admin trigger. Candidate pool sorted by modifiedTime descending before further processing — ensures newer files are processed first, which matters for test case detection on ambiguous files.

Section 12 · Phase 0

Entity inference

Entity inference determines which real-world institution a Drive file belongs to. It uses a four-signal cascade. Confidence below 0.7 triggers a manual review flag rather than automatic import.

Signal cascade

1
Assessment ID extraction — confidence 1.0
Scan filename and first 2,000 characters for pattern DMA-(?:ASM|RES)-([A-Z0-9]+)-(\d{8})-(\d{4}). The entity code (e.g., FCE, ZION, PMTCAN, SLGreen) is the canonical identifier. If the code is in the entity table → immediate match. If new → entity created as PENDING_REVIEW.
2
Entity name from document header — confidence 0.9
First 500 characters of document content. Entity name appears as a heading immediately following "CLIENT PROFILE" or "DIGITAL MATURITY ASSESSMENT". Extracted name is normalised (strip legal suffixes: ACA, NA, N.A., Corp, Inc., LLC) and fuzzy-matched against the entity table (Levenshtein ≤ 3).
3
Filename token extraction — confidence 0.75
Split filename on _, -, spaces. Strip DMA prefixes/suffixes (DMA, Assessment, Report, Research, Scoring, Workbook, FINAL, v1, v2, FINAL, 2024–2026). Match remaining tokens against entity table.

Confirmed mappings from Drive: DMA_Assessment_Report_FCE → Farm Credit East · DMA_Assessment_Report_SLGreen_FINAL → SL Green · Fulton_Bank_DMA_Assessment_Report → Fulton Bank · DMA_Client_Profile_Research_Report_Zions_Bancorporation → Zions Bancorporation · Payments_Canada_Client_Profile_Research_Report → Payments Canada

4
Parent folder name — confidence 0.65
If the file is inside a sub-folder (not Drive root), the folder name is matched against the entity table using the same fuzzy matching. E.g., a file inside a folder named "Farm Credit East" → entity = Farm Credit East.

Confidence <0.7: File placed in the UNRESOLVED queue, visible in the admin UI at /admin/import?status=unresolved. The file is not imported until an admin confirms or corrects the entity assignment. Non-DMA collateral files (e.g., Ag_Lending_Solution_Blueprint_v2) typically fall here and are excluded after admin review.

Section 14 · Phase 0

Deduplication and recency

For any given entity × artifact type, there may be multiple versions in Drive. The deduplication key is (resolved_entity_id, artifact_type). Within each key there is exactly one winner — all others are logged as SUPERSEDED.

Winner selection rules — applied in order

1
FINAL suffix wins
If any candidate has _FINAL in the filename and others do not, the FINAL version wins regardless of date. FINAL indicates analyst-approved delivery. If multiple FINAL versions exist, proceed to rule 2.
2
Assessment ID date wins
If Assessment IDs are extractable: the candidate with the highest YYYYMMDD component wins. Equal dates: higher sequence number wins. E.g., DMA-ASM-FCE-20260312-0001 beats DMA-ASM-FCE-20260201-0001.
3
Drive modifiedTime wins
Fallback when rules 1–2 do not resolve: the file with the latest modifiedTime from Drive metadata wins.
4
DMA Agent owner beats named-user owner
Final tiebreaker: a file owned by dma@zennify.com (engine-generated) wins over a manually uploaded file. The engine-generated version is the canonical output.

Section 15 · Phase 0

Import pipeline

The end-to-end flow from Drive crawl to database record. Ten sequential steps with logging at each stage.

1
Crawl trigger
Scheduled (every 6 hours) or manual (POST /api/v1/admin/import/trigger). Delta mode by default — only files with modifiedTime > last_crawl_at. Full rescan via full_rescan: true.
2
Metadata collection → candidate pool
Recursive folder traversal (§10). MIME filter applied. Candidate pool assembled in memory, sorted by modifiedTime descending.
3
Artifact classification
Each candidate classified by folder path → filename pattern → header scan (§11). Unclassified files → UNRESOLVED queue.
4
Test case filtering
All 6 detection rules applied (§13). EXCLUDED files logged to audit. REVIEW files flagged for admin. Production files proceed.
5
Entity inference
4-signal cascade (§12). Files below 0.7 confidence → UNRESOLVED. New entities → PENDING_REVIEW (not shown in directory until admin confirms).
6
Deduplication per entity × artifact type
4-rule winner selection (§14). Losers marked SUPERSEDED. One winner per entity × artifact type proceeds to content fetch.
7
Deep content fetch and parse
Winners fetched from Drive API (5 concurrent). Parsed per artifact type using section header anchors for documents and header-row detection for workbooks. Structured data written to parsed_artifact staging table.
8
Synthetic payload assembly
All parsed fields from all artifact types for one entity merged using the source priority hierarchy (§11). Fields from higher-priority sources overwrite lower-priority ones. Assessment ID set as run_id; if absent, a deterministic ID is generated: DRIVE-{entity_code}-{content_hash[:8]}.
9
Database upsert
Synthetic payload upserted into the same schema as Phase 1 payloads (idempotent on run_id). data_source: DRIVE_PARSE set. Thin-evidence alerts auto-generated from thin_flag fields.
10
Audit log and admin notification
Import summary written to import_audit: total files found, classified, excluded, resolved, imported, errors. Admin notified via SSE if new entities are PENDING_REVIEW or error count > 5.
