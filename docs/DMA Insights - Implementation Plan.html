The walking skeleton is stage 3 and it is not optional

One entity, one run, one section — synthesised by a Cowork agent, validated, promoted and rendered on screen — before any breadth is built. Every architectural assumption in this plan is falsified or confirmed by that one path, and every one of them is expensive to discover later.

One sequencing trap worth naming. It is tempting to build the frontend early against hand-written fixtures, because it is visible progress and parallelises well. Resist it until stage 3 has landed. A frontend built against fixtures encodes the fixture author's assumptions about the payload shape, and those assumptions are exactly what the contract exists to replace. Build the shell early; build the surfaces against promoted data.

Initialise the monorepo and write the instructions Claude Code reads at the start of every session. This file is the highest-leverage artefact in the repository: it is what stops a session re-deriving a decision that was already taken.

  • Monorepo: backend/, frontend/, infra/, etl/, docs/

S.2Environment configurationScaffold

Every variable the four services need, with no secret in the repository. Note what is absent: there are no model names, no inference endpoints, no temperature, no cache time-to-live.

  • An example environment file per service, committed; real values in a secret manager
  • Typed settings for the backend; typed environment access on the frontend
  • Database, cache, storage, OAuth, token and connector-credential configuration

Verification

  • No secret is committed; a pre-commit hook scans for them
  • A service fails fast with a clear message on a missing required variable
  • No configuration key references an inference provider
S.3Continuous integrationScaffold

Lint, type-check, test, build and deploy per service — plus two gates that exist specifically because of this architecture and would not appear in a conventional pipeline.

  • Migrations run as a deploy step under the migration role
  • Gate A — no inference import. The build fails if any backend module imports an inference client.
  • Gate B — the ceiling ratchet. The build fails if any corpus gate threshold in the committed configuration is higher than in the previous commit.

Verification

  • A branch adding an inference import fails CI
  • A branch raising a corpus ceiling fails CI and names the gate
Why Gate B belongs in CI: the pressure to raise a ceiling arrives exactly when everyone is busy shipping. A check at the moment of the commit is the only one that reliably resists it.
Stage 0

Infrastructure and schema

0.1Cloud project and identityInfra

One project, four service identities, least privilege throughout. The identity boundary carries real architectural weight: it is where the write-boundary invariant is enforced.

  • Service identities for web, api, mcp, worker
  • The worker identity holds read-only delegation on the assessment tree
  • The connector identity holds the only credential that can write serving tables
  • Artefact registry, secret manager, monitoring and tracing

Verification

  • The API identity cannot write beyond the two workflow tables
  • The worker identity has no access to serving or staging tables
0.2Database instance and rolesInfra

Private networking, automated backups, point-in-time recovery. Four database roles matching the four services, created before any table exists so no table is ever created without its grants.

  • PostgreSQL 16 with the vector and case-insensitive-text extensions
  • Roles for the API, connector, worker and migrations
  • Default-deny grants: a new table grants nothing until a migration says so

Verification

  • The API role returns a permission error on any staging select
  • Point-in-time recovery is verified by an actual restore, not by a console setting
0.3Deploy all 89 tablesSchema

Migrations in tier order, so a foreign key never points at a table that does not yet exist. The enumerated types are created before the tables that use them.

  • Enumerated types (22) → Auth (2) → Catalogue (21) → Ingested (13) → Ingest ops (3)
  • → Staging (3) → Serving (33) → Control and audit (7) → Workflow (5)
  • All ten stored generated columns; all check constraints; both partial unique indexes
  • Per-role grants applied in the same migration that creates each table

Verification

  • The table count in the application schema equals 89
  • Every generated column is stored, not virtual
  • An out-of-range rank score is rejected at insert
  • A null published date yields a null age, an unverified band and an undated status
  • Both partial unique indexes hold under concurrent insert
0.4Catalogue loadData

Load the capability catalogue — 851 cells across four pillars and 17 categories, plus the supporting tables, the alias bridge and the value chains. Every row is keyed on its version, so a bump adds rows rather than mutating them.

  • Ingest into the 21 catalogue tables, keyed on identifier and version
  • A version row marked current; existing runs keep their pinned version
  • The alias bridge, populated for any known rename
  • The toggle cascade — what makes scored cells differ from catalogue cells
  • Value chains and their cell mappings, which the value-chain view reads

Verification

  • Cell count equals 851; per pillar P1 205 · P2 292 · P3 164 · P4 190
  • Every cell resolves to a canonical name — none returns a raw code as its label
  • A renamed cell resolves through the alias bridge across a simulated bump
  • Every value-chain stage maps to at least one cell
0.5Cache, storage and jobsInfra

Scoped deliberately narrowly.

  • Cache: the ingest job queue, and claim leases with a time-to-live
  • Buckets: artefacts (retained, for excerpt verification), exports, corpus packs
  • Cloud Run Jobs registered: corpus-gate-scanner · pack-exporter
  • Cloud SQL is Enterprise Plus with Managed Connection Pooling; svc_mcp pools in session mode, everything else transaction mode
  • Database auth is automatic IAM via the Cloud SQL Python Connector, with pool_recycle=1800 and pool_pre_ping — tokens live one hour and pooled connections must not outlive them
  • Response compression is FastAPI middleware; Cloud Run does not compress dynamic responses
  • Memorystore for Redis is reached over Direct VPC egress

Verification

  • A claim lease expires and the run returns to unclaimed
  • Artefact bytes survive parse and are fetchable by the connector for excerpt verification
Stage 1

Ingest worker

Built before the connector, because the connector's primary read tool returns the parsed package. No ingested run means no bundle, and nothing for a Cowork agent to synthesise against.

1.1Traversal and classificationWorker

Scheduled traversal of the assessment tree, diffed against previous scans so re-running the scanner does not reprocess the corpus.

  • Read-only Drive client with delegated access
  • Folder discovery, diffed against prior scans
  • Artefact classification against the registry, ranked by source priority
  • Every file recorded — including ones that were skipped

Verification

  • A skipped folder appears in the audit with the rule that skipped it — a silently skipped folder is indistinguishable from a traversal bug
  • Re-running the scanner processes nothing new
1.2Entity resolution and deduplicationWorker

The four-signal cascade, then test-case exclusion, then the four ordered dedup rules. Exclusion runs before resolution so a rehearsal folder never becomes an entity.

  • Cascade: run manifest → request identifier → document header → folder name
  • Low confidence produces a pending-review entity, never an active one
  • Test-case detection, recorded with the rule that fired
  • Dedup: priority → completion date → parsed section count → stable tiebreak
  • The losing artefact is retained and marked, never deleted

Verification

  • A test folder never produces an entity
  • Dedup is reproducible — the same inputs select the same winner twice
  • A low-confidence inference lands in pending review and does not appear in the directory
1.3Artefact parsing — and the two fields that cannot be backfilledParser

Workbook, report, client profile and package files into the ingested tier.

  • Workbook → score rows, with the source cell on every row, and all four grain ids
  • Report and client profile → document sections, with page numbers
  • Package files → evidence, issues, peers, recommendations, tech stack, fits, firmographics
  • Artefact bytes retained in object storage, so an excerpt can be verified later
  • Every package excerpt verified against those bytes at parse time
  • Scored cells computed and stamped on the run
  • Parse observations for every disagreement, exclusion, skipped row and unparseable value

Verification

  • Every score row carries a source cell and all four grain ids
  • A missing score is skipped, never defaulted to zero — a zero renders as the lowest maturity band and is indistinguishable from a real assessment of it
  • An excerpt absent from its artefact leaves the row unverified rather than linked
  • Scored cells is stamped and differs from catalogue cells where toggles applied
Neither field can be backfilled. The originating workbook cell and the artefact bytes are only available at parse time.
1.4Embedding tier and centroidsVector

Built at ingest, because V4 needs the bundle embedded before the first submission arrives. Entirely inside the worker, off any request path.

  • Local 384-dimension sentence-embedding model in the worker and connector images — CPU, deterministic, no network call
  • Sentence-window chunking at 60–120 tokens with 20% overlap; evidence excerpts are already the right size and pass through whole
  • L2 normalisation at write, so cosine becomes a dot product
  • bundle_embeddings populated with scope, source reference and retained content — the content is what lets a flagged field be told what it matched
  • bundle_centroids per scope: cell, category, pillar, run
  • HNSW index created once at migration (m=16, ef_construction=64); the graph grows incrementally as each run's vectors insert at ingest
  • embedding_model pinned on every row

Verification

  • A run produces 3,000–6,000 vectors and four scope levels of centroid
  • A centroid with fewer than five members is marked so the check abstains
  • An insert with the wrong dimension fails at INSERT with a readable message
  • Mixed embedding models in one run is rejected, not silently averaged
  • The attribution query returns three nearest chunks in single-digit milliseconds
Scoped centroids, not one global centroid. An assessment corpus spans regulatory filings, technology detail and executive commentary; their mean points at nothing. Each claim is checked against the narrowest centroid that applies.
Stage 2

MCP connector

The contract, and the only writable boundary into served content. Everything downstream depends on it, which is why it is stage 2 rather than stage 8.

2.1Contract registry — all 34 sectionsMCP

Field tuples with per-field spec text. This registry is the single source of truth that the contract tool serves, the validator reads and the writers target — one definition, four consumers.

  • Field tuple: required, type, item type, doc; nested specs under a sections key
  • All 34 sections across 6 pages, 32 of them required
  • Every list-of-object field carries its item schema in its doc text
  • The universal envelope on every section: produced-at, producer version, citations, internal-only paths, empty state

Verification

  • Every section has a contract, and the count reconciles with the serving-table list
  • No list-of-object field lacks doc text
  • The contract tool returns doc text verbatim
The doc field is part of the contract, not documentation. Required-type-items tells the agent nothing about item keys, so the shape would live only in the writers and the agent would guess — and a guess that type-checks promotes silently wrong content.
2.2Identifier authorityMCP

One module, one compiled recogniser, imported everywhere and pinned by test at every call site.

  • The recogniser plus find-ids and find-fabricated helpers
  • Four namespaces recognised: package, enrichment mint, connector, internal
  • Case-sensitive, no partial matches, order preserved
  • Agent-creatable id validation: exactly 5 classes, rejected otherwise
  • The connector boundary's copy pinned to the same compiled object

Verification

  • A test asserts object identity of the compiled pattern at every call site, not equality
  • The mint namespace is matched
  • A payload attempting to mint an evidence id is rejected
2.3Read and discover toolsMCP

Six tools, all idempotent and side-effect free.

  • get_report_bundle — the parsed package, with a source cell on every score and all four grain ids
  • get_page_contract — shapes plus verbatim doc text
  • get_capability_catalogue — the pinned catalogue, with the alias bridge and value chains
  • get_evidence — a three-way split: found, not found, foreign
  • get_run_progress — per-page status and what is blocking
  • get_client_state and list_pending_runs — served state, prior runs, and the claim

Verification

  • Every score in the bundle carries a source cell
  • A foreign id is returned in its own bucket, not merged into not-found
  • Prior runs are returned so a rerun is not synthesised as though it were a first run
The three-way split is the point. Not-found means fabricated or unregistered. Foreign — a real row belonging to another institution — must stop synthesis rather than be filtered out quietly, because its presence means the reasoning has drifted onto the wrong entity.
2.3bEnrichment intakeMCP

The synthesis agent reaches the enrichment service directly; the application never calls it. What the application must do is accept the output as evidence and tier it correctly.

  • register_evidence accepts origin=connector and stamps it
  • Tier comes from the underlying source, never from the tool — a technographic scan registers at T1, and filing it at T4 caps the capability at L2.5
  • The source domain is identity-checked at registration, because enrichment resolves by domain and a holding company, a subsidiary and a same-named institution in another market all have one
  • A registered item with no traceable source URL is accepted as INFERENCE, never FACT

Verification

  • A technographic scan registers at T1 and does not cap its cells
  • An enrichment row whose domain fails the identity check is quarantined, not stored
  • A value with no source URL cannot be registered as FACT
2.4Validation — two passes and four gate familiesMCP

Structural and editorial first; evidence second and separately, because checking an extraction against artefact bytes is database work of a different shape from format sweeps.

  • Pass 1: required fields, types, word budgets, forbidden registers, terminal punctuation, id resolution by pattern
  • Pass 2: every id resolves and belongs to this entity and run; every excerpt verbatim against fetched bytes; every source domain identity-checked
  • Grain resolution: resolve each quoted label to a served cell, require agreement, round once
  • The identity gate: legal name, regulator, footprint, source domain, order of magnitude
  • All seven cross-surface reconciliation pairs
  • r_layer present on every ranked or causal claim, with a verdict
  • empty_state.sources_searched on every declared absence — an absence with no ladder is rejected
  • narrative_thread present on each page lead section
  • Band words validated against the four-value domain, resolved from the RAW score
  • The citation stack V1–V4, with V4 abstaining when no embedding tier is available
  • Structured verdicts: gate id, JSON path, and a message naming the arithmetic
  • The gate registry populated across all four families

Verification

  • A grain mismatch fails and the verdict names both figures and the path
  • A foreign source domain quarantines the field and emits a reason — no value is substituted
  • V4 abstains rather than failing closed when the embedding tier is unavailable
  • A verdict message is specific enough to repair from without re-reading the payload
  • All seven reconciliation pairs are asserted independently
Any evidence reason at all fails the submission. An excerpt is either a copy of something a document says or it is not evidence. The check lives at submit so the agent can still repair the span.
2.5Write tools and the promote transactionMCP

Three write tools. The promotion is one transaction spanning 6 pages and 34 writers.

  • register_evidence — server allocates the id, computes the bounded rank score, dedups by content hash scoped to the entity, verifies the excerpt, identity-checks the domain
  • submit_page_payload — validate, supersede the live row, stage, return the verdict
  • promote_run — assert a pass on every page, then all 34 writers in one transaction
  • Claim leases with expiry, so a dead session does not block a run permanently
  • Idempotent re-promotion; supersession on resubmission

Verification

  • A promote with one page missing writes nothing and returns the missing page
  • An injected writer failure rolls back all 34 writes
  • Re-promoting a promoted run is not an error
  • Registering the same source six times returns one id six times
  • Every promoted row carries a non-null producer version
2.6Inspect tools and the error taxonomyMCP

Three tools plus the structured error set. An error an agent cannot act on produces another failed attempt, so the taxonomy is part of the deliverable.

  • get_validation_verdict, get_run_progress, explain_gate
  • Gate explanations carry threshold history, with a reason per change
  • All 10 structured error codes, each with a documented agent action

Verification

  • Every error code the connector can emit appears in the documented table
  • Gate history shows direction of movement — a ceiling that only moved down is visible as such
Stage 3

Walking skeleton

One entity, one run, one section — synthesised in Cowork, validated, promoted and rendered. Nothing else is built until this path works.

1
Ingest one package
A real assessment folder, parsed, with source cells and retained bytes.
2
Connect Cowork
The connector registered, the agent claiming the run and reading the bundle.
3
Synthesise one section
overview.scores — the hero. Chosen deliberately.
4
Fail, then repair
Submit with a known grain error and repair from the verdict alone.
5
Promote and render
A minimal page reading the serving table and showing the hero.
Why overview.scores is the right first section

It exercises grain resolution, the peer-figure ladder, the composite rounding rule, the generated band column and the cross-section reconciliation gate — five of the mechanisms most likely to be subtly wrong — in one small payload.

What this stage proves

AssumptionConfirmed by
The connector is reachable from a Cowork session with its own credentialA claim acquired and a bundle read end to end
The contract is legible enough to synthesise against without reading the sourceAn agent producing from the contract tool alone
A failing verdict is actionableRepairing a grain error from the verdict without re-reading the payload
Grain resolution actually resolvesA deliberate mismatch failing, and the correct pairing passing

The serving table is readable in the shape the API needsThe hero rendering from a single indexed select
Rounding happens once and the band is generatedA tie value rendering identically on the hero and the run row

Verification

  • One run reaches promoted with one section and five explicitly empty pages.
  • The hero renders the composite, four pillar scores, peer deltas, posture and the framing sentence.
  • A deliberate grain error fails, and the verdict is sufficient to repair from.
  • The rendered composite equals the served value, and equals the run row.
  • No inference client appears anywhere in the request path.

Do not skip the deliberate failure. A validator tested only on valid payloads is a validator whose error paths are untested — and the error path is where the synthesis agent lives. The verdict has to be good enough to repair from on the first read, and the only way to know is to try.

Stage 4

Read API

4.1Scaffold and authAPI

Application factory, async database session, structured logging. Google OIDC with domain restriction, token verification and a two-layer role gate.

  • Health and readiness probes; middleware; structured JSON logging
  • OIDC callback, token issue and verification, httpOnly cookie
  • Role re-verified at the API on every request, never trusted from the frontend

Verification

  • An AE token is refused on Context and Health by the API, not only by the router
  • A token from outside the Workspace domain is refused at the OAuth client
4.2Page endpointsAPI

One endpoint per page plus the platform-detail sub-route and Health. Sections are selected concurrently, so a section that failed to promote returns no row rather than nulling columns the serialiser must then interpret.

  • 6 page endpoints, the tech-stack detail sub-route, and Health
  • The response envelope: entity, run, audience, and per-section data with source and provenance
  • Data-source attribution per section: producer, parsed or empty
  • Evidence resolution, run history and version diff
  • Corpus endpoints: directory, dashboard, alerts, patterns, search
  • Admin endpoints: imports, import audit, users
  • Two write exceptions: annotations and alert actions, in workflow tables only

Verification

  • A section with no promoted row returns an explicit empty state, not a null-filled object
  • The run history score column equals the Overview hero
  • Neither write exception touches a serving table
  • Health assembles from the four heatmap sections plus the runs table
One query for a count and its rows. A header and its KPI counts drawn from different queries will eventually disagree.
4.4Run resolution, pinning and version diffAPI

Every page endpoint resolves a run before it reads a section. Getting this wrong is how numbers change under an open page.

  • Slug → entity → active run, or the run pinned in the request
  • The envelope carries run id, sequence, active flag, promotion time, catalogue version and both cell counts
  • The diff resolver: direct comparison within a catalogue lineage; alias-bridged with the rename disclosed; degraded to category grain on a split or merge; not-comparable on a retirement
  • A composite compared across a catalogue bump is returned as approximate, with that stated
  • user_workspace read to default the pin, written on navigation

Verification

  • A pinned run is honoured and reported as not-active
  • A diff across a catalogue bump marks unbridgeable cells not-comparable rather than null
  • A cell that was retired renders as retired, never as a drop to zero
  • An entity with runs but none promoted returns a 404 naming both counts
Refuse rather than annotate. A renamed cell compared naively reads as a capability that vanished; a split cell reads as a score that halved. The resolver declines the comparison and says why.
4.3Redaction layerAPI

Walk the internal-only paths and delete them before serialisation. The frontend receives an object that never contained the field.

  • Path-walking redaction driven entirely by the payload's own marking
  • Customer audience: Context and Health return a locked state, not a partial page
  • Customer audience withholds the three internal Overview cards
  • Cohort-pattern entity ids stripped for every audience
  • Thin-evidence and quarantine markers retained for both audiences

Verification

  • No path listed in any internal-only array appears in a customer response
  • Entity ids never appear in any response, at any audience
  • The assertion runs against serialised output, not against the code that hides fields
Honesty is not internal. An assessment that states its own weaknesses is more credible than one that appears complete.

  • The maturity resolver, matching the database's generated band column exactly

5.2Shell, navigation and URL stateFrontend

  • URL-captured state: audience, heatmap view mode and grain, open panel and anchor, Health tab, insight grouping, filters

5.3All 9 global surfacesGlobal

Built here rather than deferred, because several are how an analyst diagnoses a bad ingest and an admin recovers from one.

  • G2 Dashboard — Command centre: active assessments, open alerts, insight cards, average maturity, in-progress runs. Header and KPI counts come from one query.
  • G3 Client directory — Card and table views with maturity, pillar strip, sub-vertical, source badge, open alerts and top platform fit.
  • G4 Global alert dashboard — The corpus-wide thin-evidence queue plus the cross-entity pattern finder and the waived-alert register. Virtualised.

  • G6 Run history — Per-entity run list. The score column must equal the Overview hero ring.
  • G7 Admin — Users and roles, settings and operations. Admin role required.
  • G8 Import & jobs — Ingest job status with a live stream, and the pending-review queue for low-confidence entity inferences.
  • G9 Import audit — Every file seen, classified, excluded or deduplicated, with the rule that fired.

Verification

  • A headline score in the directory uses its maturity band colour, not a fixed brand colour
  • An untiered entity renders as untiered, not a broken chip
  • Dashboard header and KPI counts come from one query and cannot disagree
  • The alert queue is interactive at corpus scale, with virtualisation active
  • Prospecting renders its search-to-begin state rather than an empty grid
  • The import audit shows every excluded file with the rule that fired
  • Run history's score column equals the Overview hero
Stage 6

The seven dashboards

All 38 client surfaces, built against promoted data rather than fixtures. Each carries a data-source attribute, because a blank surface is otherwise indistinguishable from a broken one.

Build each surface against its own contract

Every surface below has a full contract in the Surface Specification: what must be presented, why it is shaped that way, its information-sources table naming the source of truth per field, its synthesis prompt, and the gates asserted against it. Build from that document, not from this table — this one is the schedule.

Five surfaces are confidence instrumentation — O1b, O10 and O11 on the Overview, and Q3 and Q4 on Health. They tell the reader how much to trust everything else on the screen. If they flatter, every other number in the document becomes unfalsifiable. Three rules bind all five: a derived status must follow from a computed input; a percentage must render its denominator; and a threshold is either enforced or it is not a threshold.

Ceilings must be rates, not counts

A fixed count passes at one corpus size and fails at the next on arithmetic alone, with no defect introduced. And a ceiling set from an acceptance target rather than a measurement fails every build on day one, for defects the build did not introduce — which is how a gate ends up disabled wholesale.

Stage 9

Hardening and deployment

9.1Invariant testsTest

One test per invariant, named after the invariant so a failure is self-describing. These carry more weight than unit coverage here, because the failures this system is designed against are cases where the code does exactly what it says and what it says is wrong.

  • No backend module imports an inference client
  • The API database role holds no SELECT grant on any staging table
  • Promotion writes all 6 pages or none, verified by an injected writer failure
  • A payload minting an evidence id is rejected
  • A customer response contains no path listed in any internal-only array
  • Every promoted row carries a non-null producer version
  • Committed corpus ceilings are no higher than in the previous commit
  • The section registry, writer registry, serving-table list and surface register reconcile
  • The evidence recogniser is the same compiled object at every call site
  • No serving table contains a vector column — embeddings are never promoted
  • The writer registry is an ordered list and its order is stable across imports, because an unordered promote deadlocks under concurrency
  • V4 abstains and records NOT_RUN when no centroid exists, rather than failing closed
  • A re-promotion after a one-page fix rewrites every serving table and preserves the other pages
  • A read issued during a promotion sees the entire previous run, never a mixture
  • A catalogue load fails if any cell from the prior version is neither bridged nor explicitly retired
The reconciliation test is what prevents a specified surface being unauthorable. Four registries that can drift; one test that asserts they have not.
9.2Rendering testsTest

Assertions against rendered output rather than against the code that produces it — because the defect class here is a field nobody marked, and reading the marking code cannot find a field absent from it.

  • All 38 client surfaces and 9 global surfaces render for a fixture run, each with a data-source attribute
  • All 15 drilldowns open by clicking the component's own trigger
  • A drawer stacks above a modal; closing it returns rather than orphaning
  • Customer view withholds Context and Health entirely, asserted on markup
  • The alert queue is interactive at corpus scale
  • Every empty state is a sentence naming what was searched, never an error string
  • Every heatmap view mode and grain transition is reachable and linkable
9.3ObservabilityOps

Seven signals, one of which should page someone.

  • Page: a serving row with a null producer version — content reached a serving table without a promotion, which breaks the invariant everything rests on
  • Alert: any foreign-id rejection; any upward ceiling movement
  • Alert: identity quarantines above the corpus rate — a spike usually means one contaminated profile rather than many bad figures
  • Alert: repeated promotion failure on the same blocking page; ingest lag beyond a day; leases repeatedly expiring mid-synthesis
  • Structured logging and distributed tracing across the four services
9.4ProductionDeploy

Three environments, staged rollout, and one operational decision left open.

  • Local (seeded fixture run) → staging (anonymised subset, production ceilings) → production
  • Migrations under the migration role as a deploy step
  • Scheduled traversal and the nightly corpus scan
  • Backup verification by actual restore
  • Open: retention for superseded runs and verdicts. The contract requires only that a superseded run stays queryable long enough for the longitudinal surfaces to read across it.

Verification

  • A restore from backup produces a working instance
  • A staged deploy can be rolled back without a schema rollback
  • Corpus gates run nightly and their results are visible on Health

The last two checks, and the ones most likely to be skipped

Verify the customer view on rendered output rather than by reading the code, and verify the drilldowns by clicking the triggers the components define rather than by probing the DOM for overlays. Both shortcuts produce a clean result on a broken app — the first because an unmarked field is invisible to the code that hides fields, the second because the inline expansions match no overlay selector.
