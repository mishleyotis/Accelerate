Product Requirements Document

# DMA Insights

An intelligence workspace that turns a completed Digital Maturity Assessment into 47 interrogable surfaces an account executive can walk into a client meeting with. Every sentence it displays was written, cited, validated and persisted before the page was opened. The application performs no reasoning at request time.

Core thesis
A DMA produces hundreds of scored cells, hundreds of evidence items, insight cards, issue registers, peer benchmarks, financial trajectories and platform opportunity maps. Under a fifth of it reaches an AE. The rest sits in a forty-to-eighty page report and a scoring workbook. This product surfaces the remainder — selectively, with every number traceable to the cell it came from, and with an honest empty state wherever the evidence genuinely is not there.

38
client surfaces
Across seven dashboards, plus 9 global surfaces.

34
payload sections
Each synthesised, validated and promoted into one serving table.

15
drilldowns
Three shells. Every one renders from data the page already carries.

## How the product works

Upstream
The assessment
A DMA run produces a report, a scoring workbook, an evidence index and a package of structured files. Unchanged by this product.

Ingest
Package parser
Discovers the folder, classifies artefacts, resolves the entity, parses into a read-only tier the synthesis agent can read.

Synthesis
Claude Cowork
An agent reads the bundle through the MCP connector, reasons, enriches, cites, writes every surface, submits page by page, repairs against verdicts.

Promotion
MCP connector
One atomic write across all 6 pages. Nothing renders before it; nothing is half-new after it.

Serving
The web app
Pure reads. No reasoning, no model, no synthesis at request time.
The separation is the central product decision. Everything expensive, slow and fallible happens once, ahead of time, in an environment where a failure is catchable and repairable against a structured verdict. Everything an AE does at twenty to nine before a nine o'clock meeting is a database read.

The sentence the whole architecture follows from
The app never calls a model. Content arrives as a validated payload over the MCP connector and is written to the serving tables by promotion. This is what makes the product fast, cheap and reproducible — and what turns a hallucination into a build-time failure a verdict can name, rather than a runtime surprise a client discovers.

## Who it serves

Internal, and it stays internal. Zennify account executives preparing for and sitting in client conversations; delivery analysts who ran the assessment and own its quality; and practice leads who read across the corpus. A client sees output from it — a redacted view, an exported scorecard — but never the tool itself.

## What it is not

- Not a replacement for the assessment engine. It consumes assessments; it does not perform them.
- Not a scoring tool. Nothing here assigns a maturity level. Scores are read from the workbook and never re-derived.
- Not a research tool. No live scraping, no request-time search. Enrichment happens during synthesis.
- Not a chat interface. There is no prompt box, because the reasoning already happened.

Section 02

# Problem statement

Two problems sit on top of each other. The first is that rich assessment output does not reach its audience. The second is that when it does, it has to survive being challenged — and six specific defect classes determine whether it does.

## The assessment does not reach its audience

### The static artefact problem

Every completed DMA writes documents and workbooks to Drive. Reaching one finding means opening a forty-to-eighty page report and interpreting tables without context. The report alone carries twelve structured sections: an SCQA executive summary, trend analysis, an issue register with a timeline, four pillar deep-dives, benchmark comparison, gap prioritisation, recommendations with root-cause analysis, a transformation roadmap, data gaps and a full evidence registry. None of it is searchable, filterable or cross-referenceable.

### The evidence depth problem

Each score is backed by evidence carrying a quality tier, a rank score, a claim class, a source URL and a verbatim excerpt. The insight cards — each structured as what, why and so what — are the most commercially useful analysis in the engagement, and they are rows in a table on page twenty.

### The platform recommendation problem

Recommendations name platforms: Agentforce, Data Cloud, Mosaic AI, Tableau Next, Twilio Engage, nCino. Each gap maps to platform areas and features in the capability catalogue. Today that is prose, with no way to filter by platform or see every gap a platform addresses.

### The rerun quality problem

A rerun has no memory of where the prior run was thin. Cells with fewer than three evidence items get no special attention, and proxy searches that were never attempted are not recorded. Reruns reproduce the same gaps.

### The version coherence problem

Runs accumulate with no comparison mechanism. Asking whether a pillar improved means opening two workbooks and comparing rows by hand.

## Six defect classes that determine whether it survives a client

Each is closed by a specific mechanism rather than by review discipline. The pattern worth naming: every one is a contract that existed in someone's head rather than in a file. None would have been caught by more careful reading, because the fifth reader reads the same undocumented assumption as the first.

Defect class | What it looks like | Closed by

Grain  | A quoted score names a different cell than the one it came from — a sub-capability's name beside a category's mean.  | Grain lock at submit: resolve the label to a served cell, require agreement within 0.05. blocking

Identity  | One entity's overview carrying another institution's assets, regulator and footprint — one root cause visible on five surfaces at once.  | An identity gate on every figure, quote, document and source domain. blocking

Citation  | Enrichment-minted ids served having passed no citation check, because no module's pattern could see the mint namespace.  | One recogniser in one module, with a test asserting identity of the compiled object at every call site.

Bounds  | An evidence rank score rendering below the floor of its own scale.  | Server-computed, bounded, and quarantined outside the range.

Derived values  | An age column reading as uncomputable while the status beside it reads fresh.  | Computed or null, never a sentinel. Status follows band, band follows age, age follows a real date.

Coverage  | Rendered surfaces with no payload route, so nothing can author them even though they are specified.  | A complete section set, reconciled by test against the rendered surface register.

Why these matter more than they look. An AE is challenged on exactly one thing in a client meeting: where a number came from. A product that answers that instantly and correctly is worth more than one that presents more analysis. Every mechanism above exists to protect that single moment.

Section 03

# Personas and roles

AE
The account executive
Primary user · reads before a meeting
Has twenty minutes and a nine o'clock call. Needs the one number that frames the conversation, the named capability behind it, and something true and specific to open with. Will be challenged on where a figure came from and must survive that.

What is true about this client, and what do I lead with?
Where does that number come from — shown, not asserted.
What do I say out loud, in words I would actually use.

AN
The delivery analyst
Owns assessment quality
Ran the assessment and is accountable for it. Needs to see where evidence is thin, which gates failed and why, which cells are capped by tier misclassification, and what the next run should go and find.

Which cells are under-evidenced, and what would close them?
Did anything fail a gate, and is it disclosed rather than hidden?
What changed since the last run, and did a recommendation land?

PL
The practice lead
Reads across the corpus
Not interested in one client. Wants the pattern: which categories are structurally weak across a sub-vertical, where platform opportunity concentrates, and whether assessment quality is improving run over run.

What is systematically true across this sub-vertical?
Where does opportunity concentrate, and how confident are we?
Is the corpus improving, or has the gate simply loosened?

## Roles and what they gate

Role | Reaches | Cannot

AE  | Overview, Insights, Heatmap, Platform and Tech stack in either audience. All drilldowns, evidence drawers and exports.  | Reach Context or Health. Resolve alerts. Trigger a synthesis run.

ANALYST  | Everything the AE reaches, plus Context and Health — the thin-evidence queue, gate results with reasons, the evidence age tracker, cross-entity patterns and version diff.  | Manage users, reload the catalogue or administer imports.

ADMIN  | Everything, plus user management, import administration, the import audit and catalogue version control.  | Write content. Nothing writes a serving table except a promotion.

There is a fourth reader who never signs in: the client. The customer view is a redaction contract driven by payload marking, not a layout preference. Two whole dashboards — Context and Health — are withheld from it entirely.

Section 04

# The synthesis model

Content is produced by an agent running in Claude Cowork, connected to the application through the DMA Insights MCP connector. The connector is the only writable boundary into anything the product serves.

```
┌─ CLAUDE COWORK ───────────────────────────────────────────────────────┐
│  A synthesis agent running the DMA surface-production skill.          │
│  Reads the assessment. Reasons over it. Searches for what would       │
│  refute it. Enriches where evidence is thin. Writes every sentence    │
│  the product will display, and cites all of it.                       │
└───────────────────────────────┬───────────────────────────────────────┘
                                │  DMA Insights MCP connector · 12 tools
                                │  read:  bundle · contract · catalogue · evidence · state
                                │  write: register_evidence · submit_page_payload · promote_run
                                ▼
┌───────────────────────────────────────────────────────────────────────┐
│  THE APPLICATION       validates → stages → promotes → serves         │
└───────────────────────────────────────────────────────────────────────┘
```

Claude Cowork and Claude Code are different things in this system
Claude Cowork is where synthesis runs: an agent reads the assessment through the MCP connector and writes the content the product serves. Claude Code is where the application itself is built, and it never touches client content. They are separate trust boundaries and the documents keep them apart.

## Why synthesis happens in Cowork

Property | What it buys

It is agentic and multi-step  | Producing one client means reading a bundle, resolving a catalogue, reasoning across 34 sections, running enrichment searches, registering sources, submitting, reading verdicts and repairing. That is a long-running task with many tool calls, not a single completion.

It can search  | Enrichment is the highest-value work on any surface. A cell with two evidence items and a successful search becomes a cited cell; the same cell without one becomes a thin-evidence alert.

It is separable from the app  | The deployed application carries no inference dependency, no model credential, no token cost and no latency budget for reasoning. Its compliance surface shrinks to reads.

It fails where failure is cheap  | A grain violation caught at submit is repaired in the same session. The same violation discovered in a client meeting is not repairable at all.

## Enrichment: Clay

Clay closes the evidence gaps public search cannot. It runs during synthesis, immediately after the package is read and before the pages that consume it, because enrichment is asynchronous and the surfaces that need it come last.

Surface | Provides | Data point | Tier

O7 | Leadership | find-and-enrich-contacts-at-company — filtered contact rows | —

O12 | Thought leadership | add-contact-data-points — Find Thought Leadership | T2–T3

O2 | Firmographics | add-company-data-points — Annual Revenue · Headcount Growth | T1–T2

T1 | Technology stack | add-company-data-points — Tech Stack | T1

O3 | Why-now signals | add-company-data-points — Recent News · Latest Funding · Open Jobs | T2–T3

C5 | Acquisitions | add-company-data-points — Recent News + Custom | T3

P1 | Platform readiness | add-company-data-points — Open Jobs — the demand signal | T2–T3

O7 | Tenure and trajectory | add-contact-data-points — Summarize Work History | T3

Three rules that matter more than the call sequence
Cite the source, not the tool. A value Clay surfaced is evidence because of the filing behind it, not because it arrived through an API — a value with no traceable source is an inference and is labelled one. Never record an absence from a Clay call without polling first; the search response carries base fields only, so an empty leadership panel written before the poll resolved is an unfinished call rendered as a finding. And enrichment is a budget, not a blank cheque — a technographic scan is worth its credits, enriching the whole org chart is not.

Per run | Call | Scope

1 | company enrichment call | Tech Stack · Annual Revenue · Headcount Growth · Recent News · Open Jobs · Latest Funding

1 | leadership contact search | C-suite and technology leadership, title-filtered

1 | contact enrichment call | Find Thought Leadership · Summarize Work History

0–2 | targeted custom data points | Only against a named gap already attempted by search

A technographic scan is a T1 machine scan, never T4. Filing it at T4 caps the capability at L2.5 and silently suppresses the score — the commonest tier misclassification in the corpus, and Clay is now the largest single producer of these scans.

## The agent's responsibilities

- Reading the parsed package, the page contract and the catalogue pinned to the run.
- Reasoning over evidence and writing the prose every surface renders.
- Enriching beyond the package when a cell is thin — and registering every source found before citing it.
- Challenging its own conclusions: state the claim, search for what would refute it, probe for grain mismatch and identity contamination, then accept, reject or mark uncertain.
- Emitting honest empty states, with what was searched, rather than filling space.
- Marking every internal rung in the payload so the serve layer can strip it.

## What the agent is forbidden from doing

- Assigning a score. Scores are read from the workbook and never re-derived.
- Inventing an identifier. It creates 5 classes — insight card, finding, focus area, tech-stack row and why-now signal — and everything else is read or requested.
- Choosing an evidence id. Enrichment sources are registered and the server allocates the id.
- Computing an evidence rank score. The server computes it, bounded.
- Writing a serving table. Every write goes through the connector; there is no side door.

The rule that prevents most errors
An invented evidence id is fabrication by construction, even when a matching source genuinely exists. Register first, cite second, and use the id you were given.

## The analyst stance

The agent extracts and explains. It is not a copywriter and not a scorer. Every claim about the client carries an evidence id; if it cannot be cited, it is not written. Where a source is absent, the surface renders an honest empty state — absent beats wrong, because a guessed field survives into a meeting and costs credibility, while a dash with a provenance note costs nothing.

## The reasoning layer

Every gate in this product checks a claim after it has been written. The reasoning layer is what happens before, and it is the only mechanism that catches a claim that is well-formed, correctly cited, grain-locked and wrong.

 | Step | What it requires

A | Hypothesis | State the claim and its confidence, before defending it.

B | Counter-evidence | Argue the strongest case against it. Inside a thin margin, present both and say the call is close.

C | Domain test | Is this plausible for THIS sub-vertical, size tier and regulator?

D | Failure probes | Run the probe set for the surface. Each probe fires a search.

E | Verdict | ACCEPT · REJECT · UNCERTAIN. Reject means re-rank or drop, not soften.

Any surface making a ranked, causal or comparative claim carries its verdict in the payload. A verdict that is not recorded is a step the agent can convince itself it took.

Step B is the one that gets skipped. Arguing against your own conclusion feels like undermining the work; it is the opposite. A claim that survives its strongest counter-argument is one an AE can defend in the room, and a claim that does not survive was going to fail there instead. The strongest form sources the falsifier from the client's own words rather than from the assessment's judgement.

### Nine contradiction classes

Each has been observed, and each renders plausibly.

Class | Looks like | Caught by

Grain | A figure quoted under a name from a different row | Grain lock, per quoted figure

Magnitude | Two figures for one metric differing by more than a quarter | Identity gate, assertion 5

Cross-surface | The hero names one constraint and the findings another | The seven reconciliation pairs

Source rank | The workbook and the report disagree and the report won | Source priority — the workbook wins on scores

Self-description | The entity's claim contradicts a registry | Registry wins; the contradiction is itself a finding

Arithmetic vs analyst | The engine ranks a platform the report never discusses | State it, say which won, lower confidence

Temporal | The timeline shows a platform live; the register shows it stalled | One is wrong, or the relationship is the finding

Confidence | A cell scored HIGH on two evidence items | Confidence is earned by the evidence count

Vocabulary | One word carrying two meanings on one screen | Resolve the band word from the served score

Never average two disagreeing figures
The result is in no source, which is fabrication with extra steps. Agreement from independent origins is corroboration. Disagreement where one source outranks resolves by priority and is recorded. Disagreement between peers is quarantined and stated — the resolution is the finding.

## Register discipline

Banned in anything a client reads | Why

Consultant register — leverage, journey, best-in-class | Says nothing, and signals a template.

Deficit framing — lacks, fails to | The client is in the room. State what is true, not what is missing about them.

Raw taxonomy codes in prose | Internal grammar. Capability names are humanised; codes appear only in drilldown provenance.

Score-predicate openers | A card opening with a score has told the AE nothing they cannot read off the grid.

Markdown in a field that renders as text | Only explicitly typed markdown fields go through a stripper; everything else renders literally.

## Every gap is stated as available value

Everything on a client dashboard is read by, or in front of, the client. A gap stated as a deficiency invites defensiveness; the same gap stated as available value invites a conversation. The finding is identical and the evidence is unchanged — what differs is whether the sentence is about what the institution failed to do or about what is now available to it.

Instead of | Write

The bank lacks covenant monitoring | Covenant monitoring is purchased and not yet activated

Failure to govern agent creation | Governance is in place at the sanctioned tool; the unsanctioned path is still open

Data quality is poor | Data quality rules are embedded in the delivery lifecycle; coverage extends to 7 of 12 sources

They are behind their peers | The peer set has moved on this; the pattern is available and the substrate is already built

Nobody owns the agent estate | An owner per agent is the output of one governance session

The pattern behind every rewrite: name what exists before naming what does not. Almost every gap sits beside something the institution has already built, bought or decided. Lead with that, and the gap becomes the next step rather than an indictment.

This is register, not softening. Thin-evidence markers, quarantine notes and failing safeguard gates all still render, unhedged. Never soften a risk into vagueness — state it plainly, attach it to evidence, and frame the response as available rather than overdue. Capability sits with institutions, not individuals: "the team lacks" is both accusatory and unfalsifiable.

## The verb is governed by the evidence level

Level | Basis | Permitted language

L1 | Vendor named in a T1 or T2 source with deployment confirmed | implemented · deployed · uses · powers

L2 | Official partnership announcement or case study | partnered with · selected · announced

L3 | Two or more independent signals | likely uses · signals suggest · inferred from hiring

L4 | A single weak source | may use · potential · unconfirmed

Writing “uses” on level-three evidence is a fabrication, not a style choice.

Section 05

# Dashboard architecture

Seven client dashboards, 38 client surfaces, 9 global surfaces and 34 payload sections across 6 submission pages. These are four different quantities and this document keeps them apart.

## The four quantities

Quantity | Count | What it is

Dashboard | 7 | A client screen with a route and a tab.

Surface | 38  | One card or panel a human sees on a client dashboard. Several live on one page, and one section can produce more than one.

Section | 34  | One named block inside a page payload — the unit the agent synthesises into and the unit that promotes into a serving table.

Page | 6  | A submission boundary, not necessarily a screen. Promotion requires a pass on every one.

Why the page count is load-bearing, and why sections do not follow screens
Adding a seventh page raises the bar for every client in the corpus, because promotion requires a passing submission on every page before serving tables can be touched again. Adding a section to an existing page does not. That is why four sections synthesised into the heatmap page render on the Health dashboard, and why the Context financial trajectory renders the Overview's section rather than owning one of its own.

13 surfaces · 12 sections · the page an AE is guaranteed to read

Answers one question: what is true about this client, and what do I lead with. The hero carries the whole argument in one screen — composite, four pillar scores with peer deltas, posture, and a framing sentence that states the gap, quantifies it and localises it. Five of its cards are confidence instrumentation: they tell the reader how much to trust everything else on the screen.

D2

Insights
2 surfaces · 2 sections · triage, not a grid

Insight cards grouped by priority, pillar or theme, each opening a four-tab modal carrying the full argument. The technology landscape strip sits here rather than on the Tech stack page, because the gap it names is what makes an insight actionable.

D3

Heatmap
5 surfaces · 9 sections · three view modes, four grain levels

The scoring grid and everything that qualifies it. Three view modes — focus areas, the standard grid and the value chain — and within the standard grid four grain levels: pillar, category, capability and sub-capability. This page carries nine sections because an agent filling cell evidence is already reading the workbook cell by cell; four of those sections render on the Health dashboard.

D4

Platform
5 surfaces · 5 sections · fit is not readiness

Fit score, client-specific story, gap-to-platform mapping with backing sub-capabilities, readiness prerequisites, recommendations, roadmap phases, the stair-step curve and the conversation starters. All five sections sit together because all five reference the same recommendation ids.

D5

Context INTERNAL ONLY
6 surfaces · 5 sections · withheld from the customer view entirely

Timeline, issue register, regulatory standing, sentiment, acquisition history and the financial trajectory. This is internal team-preparation material: the customer view renders a locked state, not a redacted page.

D6

Tech stack
2 surfaces · 1 section · layered, not flat

Four layer cards — operations and core, customer engagement, data and analytics, infrastructure and cloud — each with a pillar tag and a detection count. The layering carries analysis a flat list cannot: two of four detected at the data layer with a data-pillar tag says where the gap is and which pillar absorbs it.

D7

Health ANALYST ONLY
5 surfaces · 4 sections from the heatmap page, plus one derived

Five tabs: thin-evidence alerts, version diff, safeguard gates, the evidence age tracker and cross-entity patterns. This is where the assessment states its own weaknesses. Four surfaces are synthesised into the heatmap page; version diff is derived from the runs table.

# Evidence and citation

A citation is the only thing standing between analysis and assertion. This section defines what a citation has to survive.

## Two legal origins, and only two

Package evidence
Already in the store with an entity, a run, a tier and a URL. Cite it; never create it.

Enrichment mints

## The evidence rank score

```

High ≥ 3.5      Medium 2.5–3.5      Low < 2.5

               general / vague

               single T4–T5
```

Server-computed, and bounded

## Four failure modes, ordered by damage

Failure | What the client sees | Caught by

Fabricated — no such row | A chip that opens nothing | Pattern and database existence checks, fail-closed

Foreign — a real row, another entity | A competitor's data on their page | Cohort filter plus the identity gate. Stops synthesis; it is not filtered out quietly.

Misattributed — real row, wrong cell | Evidence that does not support the claim | Linker thresholds. The quietest failure: everything renders and nothing breaks.

Unverifiable excerpt | A quote that is not in the source | Verified against the fetched artefact at registration

Link on substance, not proximity. An item supports a cell when it speaks to that capability, not when it was found while researching the category. The commonest cause of over-linking is one category-level search mapped identically onto five sub-capabilities. And a cell whose every drawer is empty is a linking failure, not an evidence gap — enriching a linker bug adds evidence that also will not render.

## When an id cannot be established

In order, stopping at the first that applies:

- Enrich. Find a real source, register it, cite the returned id. This is the answer most of the time and the highest-value work on any surface.
- Drop the claim, keep the surface. A shorter honest card beats a complete unfounded one.
- Emit the empty state with what was searched. Absence with a recorded search is a finding. Absence with no record is a research failure wearing a finding's clothes.

- Never keep the claim and remove the citation. An uncited claim is excluded by the serve layer anyway, so it is wasted work as well as wrong.

# Quality gates and disclosure

Four families with four different jobs and four different failure behaviours. The prefix is part of the id, so a gate reference is unambiguous in isolation.

AG-nn Analytical

SG-nn Safeguard
At submit — and the results render to the client On failureRecorded and disclosed. Does not block promotion.ExamplesSG-01 Source diversity · SG-04 Evidence per cell

Two more run at submit and are not G-numbered because they are structural rather than analytical: the contract pass — required fields, types, word budgets, forbidden registers, terminal punctuation, id resolution — and the evidence pass, in which every id resolves and belongs to this entity and this run, every excerpt is verbatim, and every source domain is identity-checked.

Any evidence reason fails the submission
An excerpt is either a copy of something a document says or it is not evidence. The check lives at submit rather than at promotion, so the agent can still repair the span.

## Safeguard gates render to the client — three consequences

Requirement | Because

Plain language. A human sentence beside every gate, never a bare code.  | A client reading a code and a fail learns nothing and distrusts everything.

A third state. Not-run, with a reason.  | A gate that reports pass because it did not run is worse than one that reports fail.

A failing gate is not a blocked run.  | Disclosure is the point. The assessment ships with its weakness stated.

## Corpus ceilings only ever move down

Every ceiling is a measurement of the corpus as it is, so any regression past today's state fails the build. The only sanctioned movement is downward, after a defect class is fixed and re-measured. A ceiling raised to make a build pass is a gate that has stopped measuring anything — and the change history is what makes that visible.

Two corollaries. Ceilings must be per-client rates, not fixed counts: a fixed count passes at one corpus size and fails at the next on arithmetic alone, with no defect introduced. And a ceiling set from an acceptance target rather than a measurement fails every build on day one, for defects the build did not introduce — which is how a gate ends up disabled wholesale.

## Four presentation guarantees the payload must satisfy

Guarantee | Because

Order is meaning. A list renders in the order sent.  | Findings are ranked, phases sequenced, events chronological. Never rely on the client to sort.

Counts are computed. Where a surface declares its grounding, the number is the length of the citation array.  | An asserted count drifts from the thing it counts. A computed one cannot.

Denominators are rendered.  | A percentage without its base is not information. Share of cells with at least one item and share meeting the three-item threshold differ by tens of points.

Thresholds are enforced or they are not thresholds.  | A row below a declared threshold displayed under a header stating it teaches the reader to distrust every other number on the page.

## Before stating no: the proxy ladder

An absence is a finding only if the search that established it can be shown. An absence with no record is a research failure wearing a finding's clothes — and it is the difference between "no enforcement actions were found" and "no enforcement actions exist".

The rule
No empty state is emitted until a documented proxy ladder has failed. Every rung attempted is recorded, whether it hit or missed, and the record ships with the payload and renders in the empty state.

Result | Means | Renders as

HIT | A rung returned something | The finding, cited

NEGATIVE | Every rung ran and returned nothing | A verified absence, with the routes shown

NEGATIVE AND APPROPRIATE | The absence is the correct posture, not a gap | The absence, stated as correct — with why

NOT ATTEMPTED | The ladder did not run | Not an absence. Emit nothing and record the omission

The third is the one most often missed. Some absences are the correct posture rather than a gap — an institution with no browser-automation estate has declined a capability its model does not need, and saying so is more useful than rendering it as a shortfall. The fourth is the one that causes damage: an unrun ladder rendered as "none found" is a claim nobody earned.

## Representing absence

An empty surface is a value, not an omission. A missing required field fails the contract; an explicit empty state passes and renders correctly.

Situation | The payload emits | The app renders

No leadership found after a full search | An empty roster, verified-absent, and the sources searched | The honest empty state, with what was searched

Fewer than three dated financial points | The points, verified-sparse, no trend | The points, labelled a snapshot

No stair-step derivable | A null ladder and a stated reason | The reason, not a blank card

A figure failed the identity gate | A null value, quarantined, with its reason | A dash with a provenance note

A cell's evidence is genuinely thin | Thin, the sources searched, the closure condition | The provisional-score state

## A page tells one story

A page is not a container for surfaces. An AE reads it top to bottom in about ninety seconds and takes one argument away. Surfaces that are individually correct and collectively incoherent are a page that has failed, even though every gate passed.

Each page payload carries a narrative thread of 45–75 words tracing the line through its surfaces in render order. It is written last, from what was actually produced — a thread written in advance describes the page the agent meant to make. Three arguments run across pages and must not fracture: the primary constraint (hero framing → top finding → act-now insight → platform readiness → roadmap phase one), the clock (why-now → triage → horizon → cost of waiting), and the confidence (coverage → tier distribution → ceilings → thin alerts → gate results).

A page that does not cohere is more expensive than a page with a thin card on it. The thin card costs one surface; the incoherent page costs the AE the argument.

No payload field carries a hex value, a class name or an outline instruction — the payload carries the raw score, the band word where a surface renders one, and semantic flags. Thin evidence adds a dashed outline and does not change the fill, because the fill means maturity and nothing else.

Band | Word | Boundary | Fill

## Test case exclusion and deduplication

Detection runs before entity resolution, so a rehearsal folder never becomes an entity. 1

2

3

## The identity gate

Resolution establishes which entity a run belongs to. The identity gate is stricter and runs per figure, per quote, per document and per source domain, every time.

# | Assert | Catches

1 | Legal name matches, with suffixes and trading names resolved | A same-named institution in another market

2 | Regulator matches this entity's own | A regulator from another charter type — an instant contradiction

3 | Footprint and jurisdictions are consistent | The fastest contamination check available

4 | Source domain belongs to this entity or a known neutral registry | The cheapest check, and the one that catches the most

5 | Order of magnitude agrees with any other figure for the same metric | Two figures for one metric differing materially — a contradiction to resolve, not two data points to render

On failure
Quarantine the field, emit the reason, escalate. Never render a partial identity and never substitute a plausible value.

# Lifecycle and persistence

```
claim ──▶ synthesise ──▶ [register_evidence]* ──▶ submit ──▶ verdict
                                                       │           │
                                               fail ◀──┘           │ pass
                                                 │                 ▼
                                                 └── repair ──▶ STAGED
                                                                   │
                            all 6 pages STAGED + pass ───┤
                                                                   ▼
                                                             promote_run
                                                                   │
                                                                   ▼
                                                             SERVING (renders)
```

The distinction that causes the most confusion
Accepted means staged. Rendered means promoted. A submission that passes validation appears nowhere a human can see it. The two states exist so a run can be assembled surface by surface without a client ever seeing a half-built page.

## The six states

State | What is true

Claimed | One Cowork session holds a lease so two cannot synthesise the same run concurrently. The lease expires, so a dead session cannot block a run permanently.

Synthesising | Reading the bundle, the contract and the catalogue; reasoning; enriching; citing; writing.

Submitted | One page's payload handed over and a structured verdict returned naming the gate, the path and the arithmetic.

Staged | Passed validation. Persisted. Survives the session ending. Renders nowhere.

Promoted | Every page passed and all 34 sections wrote into serving tables inside one transaction.

Superseded | A newer run is active. This one stays queryable for the longitudinal surfaces.

## Three rules that make iteration safe

Rule | Consequence

Resubmission supersedes. A new submission for the same run and page replaces the previous row.  | No merge, no accumulation, no cleanup. Submit, read the verdict, repair, resubmit.

Promotion is all-or-nothing. A pass is required for every page.  | A client is never looking at a page from the new run beside a page from the old one.

Re-promotion is idempotent. | Not an error. Retries are safe.

## Three tiers, one direction

Tier | Written by | Read by | Mutability

Ingested | The package parser, at ingest | The synthesis agent, through the bundle | Read-only after parse

Staging | The connector, at submit | The connector, at promote | Superseded, never merged

Serving | The connector, at promote, only | The API, for every request | Replaced atomically per run

The boundary that matters most
The API reads serving tables only. If a surface can render from a staging table, the boundary has been broken and unvalidated content can reach a client.

## Every serving row carries its provenance

Which run produced it, which client it belongs to, when it began rendering, which synthesis version produced it, whether it is analyst, derived or producer content, and every citation behind it.

Provenance is not cosmetic. A deterministically composed recommendation must not present as an analyst recommendation, because an AE who quotes a synthetic recommendation as analyst judgement is exposed in the room.

## Reruns

A new run does not delete the old one. Promotion swaps which run is active; the previous stays queryable because the longitudinal surfaces — velocity, recurring themes, the seen-in-N-runs chip, version diff — read across runs. A rerun must not be synthesised as though it were a first run. A catalogue version bump invalidates by version tag, and renamed cells resolve through the alias bridge rather than silently vanishing.

The artefact whose absence set each ceiling.  | Category, named artefact, searchable description | Next run's research backlog

Tier misclassification
Machine scans filed at a tier that caps the cell artificially.  | Evidence id, filed tier, correct tier | Immediate correction

The limiting absence is the highest-value signal. A ceiling set by absence obliges the analyst to have looked, and naming the artefact that would raise it turns a dead end into next run's backlog. “No dedicated transformation office is evidenced” is searchable. “Insufficient evidence” is not.

## The corpus as a calibration baseline

Across the corpus the product holds every score, every peer figure and every evidence count that produced them. That makes it the natural baseline for two questions the assessment engine cannot answer alone: whether a given score is an outlier for its sub-vertical and size tier, and whether coverage is improving run over run or the gate has simply loosened.

## Longitudinal surfaces depend on prior runs

Velocity, recurring themes, the seen-in-N-runs chip and version diff all read across runs. This is why prior-run state is part of the synthesis input rather than an optional lookup.

Section 16

# Success metrics

Two sets. Integrity tells us whether the product deserves to be used; adoption tells us whether it is.

## Integrity — primary

Grain violations per client
Quoted figures that do not resolve to the cell they name. Enforced at submit, measured corpus-wide, and the ratchet only moves down.

Identity quarantines per client
Counted, not minimised — a quarantine is the gate working. The failure signal is one that should have fired and did not, caught by cross-surface reconciliation.

Unresolvable citation rate
Chips that open nothing. Target zero, enforced at submit rather than measured after.

Evidence coverage per pillar
Against the hard gate, per pillar rather than overall. An overall figure can hide a failing pillar.

Surface completeness
All 38 client surfaces exported and rendering, each declaring its data source. Target 100%.

Honest empty states
Share of absences carrying what was searched. An absence with no record is a research failure wearing a finding's clothes.

## Adoption — secondary

Metric | Target | What it tells us

Runs opened before a client meeting | 80% of active opportunities | Whether it reaches the moment it was built for

Evidence drawer opens per session | five or more | Whether AEs trust it enough to check it — the drawer is where a challenge is survived

Thin-evidence alerts resolved within 14 days of a rerun | 80% | Whether the feedback loop is closing

Conversation starters used verbatim | tracked, not targeted | Whether the prose is say-it-aloud or merely correct

Customer view exports per engagement | at least one | Whether the redaction contract is trusted in front of a client

Synthesis runs reaching promotion on first pass | rising | Whether the contract and verdicts are legible enough to work against

One class of metric deliberately absent. There is no target for time-to-first-token, synthesis latency or model cost per session. The app performs no reasoning at request time, so the interesting question is not how fast it thinks.

Section 18

# Versioning across assessments

Four independent version axes. Conflating any two produces a comparison that looks valid and is not.

Axis | Carried by | What it means

Run | run_id · run_seq | One complete assessment of one entity at one point in time. Promotion swaps which run is active; prior runs stay queryable forever.

Catalogue | ccg_catalog_version | Which capability catalogue the run was scored against. Pinned at ingest and never changed for that run.

Producer | producer_version | Which synthesis produced each section. Stamped per serving row, so one page can be re-synthesised without a rerun.

Contract | contract_version | The payload shape a submission validated against. A contract bump invalidates staged-but-unpromoted work for the changed sections only.

## What a comparison may assert

Comparison | Permitted

Two runs, same catalogue version | Cell by cell. Score, coverage and evidence deltas; recommendation carry-over.

Catalogue bump, cell bridged by an alias | Cell by cell, with the rename disclosed.

Catalogue bump, cell split or merged | Category level only. The row says not comparable, and why.

Catalogue bump, cell retired | Not comparable. Rendered as retired, never as a drop to zero.

Composite across a catalogue bump | Disclosed as approximate. The denominator changed.

Anything across entities | Never on a client surface.

The failure this prevents
A renamed cell compared naively across a catalogue bump reads as a capability that vanished — which looks like a regression, gets investigated as one, and is a rename. A split cell reads as a score that halved. Both are the diff asserting more than the data supports, and both are prevented by refusing the comparison rather than annotating it afterwards.

## Fixing one card without rerunning the assessment

A section can be wrong without the assessment being wrong. Because promoted staging rows are retained, a Cowork session can re-claim a promoted run, resubmit one page, and re-promote — five pages come from the retained rows, one from the new submission, and all sections rewrite in a single transaction. The atomic guarantee is unaffected; what changes is that five pages needed no re-synthesis.

This is why promotion retains its inputs. If promotion cleared them, fixing one card would mean re-synthesising every page — which in practice means nobody fixes one card.

Section 19

# Persistence across users and sessions

Five classes of state with five owners and five lifetimes. The common design error is treating content as user state, or view state as server state.

Class | Owner | Lives in

Content | Global — identical for every user | Serving tables, keyed by run

Synthesis session | One Cowork session at a time | Staging tables, plus a lease

User workspace | Per user, per entity | Workflow tables

View state | Per user, per tab | The URL — nothing server-side

Pinned run | Per user, per entity | URL parameter, defaulted from the workspace row

## Two AEs, one client

Both resolve to the active run and read the same serving rows. Both see identical numbers, prose and citations. What can differ: the audience (a URL parameter, not a user attribute), the pinned run, view state, and which tabs their role reaches. Content is never per-user. There is no per-user copy of a payload, no per-user cache, and nothing to reconcile between two readers.

## A promotion lands while a page is open

```
t0   AE opens the Overview            → resolves run 2, pins it in the URL
t1   Cowork promotes run 3           → run 2 becomes superseded
t2   AE clicks the Heatmap tab       → still run 2
t3   A banner offers the newer assessment
t4   AE clicks through               → the whole shell reloads on run 3

The numbers never change under an open page.
```

Why pinning is not optional
An AE reads the hero, walks into a meeting, and refers back to the tab twenty minutes later. If the run swapped in between, the figure they quoted is no longer on screen and they cannot tell whether they misread it or the data moved. Pinning costs one URL parameter and removes the entire class of failure.

## A Cowork session dies mid-synthesis

Staged work persists, including the failing verdicts. The lease expires and the run returns to unclaimed. A new session claims it, reads run progress, and continues from where the first left off — repairing the pages that failed and never re-synthesising the ones that passed.

## Concurrency

Situation | Behaviour

Two Cowork sessions, same run | The second is refused. The lease is exclusive.

Two Cowork sessions, different runs of one entity | Allowed. Whichever promotes last becomes active.

An AE annotates a run that is then superseded | The annotation stays attached to the run it was made against.

An alert is resolved, then a rerun reopens the cell | A new alert row. The reopening is itself a signal — the closure condition did not hold.

## What survives what

Event | Survives | Does not

A user signs out | Annotations, alert dispositions, last-viewed run, saved searches | View state, unless the URL was saved

A Cowork session ends | Staged submissions, verdicts, registered evidence | The claim lease, once expired

A run is superseded | Everything — scores, evidence, sections, verdicts, annotations | Its active status only

A catalogue bump | Every existing run, against its pinned version | Naive cross-version cell comparison

A contract change | Promoted content, until re-synthesised | Staged-but-unpromoted work for changed sections

# Scope

#### In scope — v1

- Internal tool for Zennify AEs, analysts and practice leads
- Package ingest from Drive with classification, entity resolution and deduplication
- The DMA Insights MCP connector — all 12 tools — as the sole writable boundary

- The full drilldown atlas — three shells, 15 panels, with stacking
- Identity, grain and cross-surface reconciliation gates, blocking

- Internal and customer audiences driven by payload marking
- Thin-evidence queue and the feedback signals back to the assessment engine
- Run history, superseded-run querying, version diff and longitudinal surfaces
- Scorecard export with redaction applied at render
- Corpus gate scanning at build time, with a downward-only ratchet

#### Out of scope — v1

- Any model call on the request path
- A customer-facing portal — clients receive exports, not logins
- Live research or scraping at request time
- Assigning or adjusting maturity scores
- Replacing the assessment execution engine
- CRM write-back
- A natural-language query interface
- Cost, ROI or investment projections
- Multi-tenant or white-label deployment
- Cross-entity patterns on any client-visible surface
- Unattended synthesis scheduling

## Deferred, with a reason

Deferred | Why not now | Revisit when

Semantic evidence search | The embedding tier serves build-time grounding validation. Exposing it as a query surface reintroduces a request-time model dependency. | Grounding validation is stable and the cost is understood.

A seventh payload page | Promotion requires a pass on every page, so a seventh raises the bar for every client in the corpus. | Only if a surface genuinely cannot be synthesised from an existing page's context.

Cross-entity patterns for AEs | It is the one surface where one client's data can leak into another's view. | Counts-and-shares-only rendering is verified on rendered output.

Unattended synthesis | Verdicts need a human in the loop while gate thresholds settle. | Corpus ceilings have moved down twice without a manual override.

The invariants — breaking any of these is a breaking change, not a refactor
The app never calls a model at request time. All content writes go through the MCP connector. The API reads serving tables only. Promotion is atomic across all 6 pages. The agent creates 5 id classes and no others. Evidence ids are recognised by one pattern in one module. Rank scores are server-computed and bounded. A quoted figure and its named cell are the same cell. Every figure passes the identity gate. A derived value is computed or null. Internal rungs are marked in the payload. A corpus ceiling only ever moves down.
