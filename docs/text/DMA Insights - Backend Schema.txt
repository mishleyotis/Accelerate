# DMA Insights — database design

PostgreSQL 16 on Cloud SQL. 89 tables across eight groups, arranged in three tiers with one direction of flow.

Engine: PostgreSQL 16 · pgvector (build-time grounding only) · Redis 7 (ingest queue and claim leases only) · Python 3.12 + FastAPI · SQLAlchemy 2.0 async · Alembic · Cloud Run

## Three tiers, one direction

Tier 1
Ingested
Written by the package parser, at ingest. Read by the Cowork synthesis agent, through the report bundle. Mutability read-only after parse.

Tier 2
Staging
Written by the connector, at submit. Read by the connector, at promote. Never by the API. Mutability superseded, never merged.

Tier 3
Serving
Written by the connector, at promote, only. Read by the API, for every request. Mutability replaced atomically per run.

The boundary the whole design rests on
The API reads serving tables only. If a surface can render from a staging table, the boundary has been broken and unvalidated content can reach a client. This is enforced by database grant, not by code convention — the API role has no SELECT on any staging table, so the query fails in local integration tests rather than in code review.

The reconciliation that must hold
 34 payload sections → 34 serving tables, of which 33 are dedicated and one is evidence_index, reused because heatmap.evidence promotes into the ingested evidence table rather than duplicating it. A test asserts this reconciles against the writer registry and the surface register.

One table per section, deliberately
 One-to-one keeps the writer simple, makes a partial write impossible to hide, and lets the API select exactly what a surface needs rather than filtering a wide polymorphic table at read time.

## The promote transaction

```
BEGIN;
  -- 1. Assert a PASS row for every page. Otherwise 409, write nothing.
  SELECT page FROM submissions
   WHERE run_id = :run AND superseded_at IS NULL AND status = 'PASS';
  -- must return all 6 pages

  -- 2. Deactivate the previous active run for this entity.
  UPDATE runs SET is_active = FALSE, status = 'SUPERSEDED'
   WHERE entity_id = :entity AND is_active;

  -- 3. Run WRITERS[section] for each of the 34 sections:
  --    delete-then-insert per serving table, scoped to (run_id).
  -- 4. Stamp promoted_at, producer_version and provenance on every row.
  -- 5. Mark the staging rows promoted.

  UPDATE runs SET is_active = TRUE, status = 'PROMOTED', promoted_at = now()
   WHERE id = :run;
COMMIT;
```

On any writer failure the transaction rolls back and nothing is written — there is no partial promote, so a client is never looking at a page from the new run beside a page from the old one. Re-promoting an already promoted run reaches the same state and is not an error.

```
-- Exactly one active run per entity
CREATE UNIQUE INDEX runs_active_uq ON runs (entity_id) WHERE is_active;
```

## The band domain is four values, not five

```
-- The resolver has four branches. Anything at or above 4.0 returns
-- Differentiating, so a fifth enum value would be unreachable and would
-- let a writer emit a band no renderer produces.
CREATE TYPE band_t AS ENUM
  ('Activating','Building','Competing','Differentiating');

-- Generated from the RAW score, before display rounding. 2.97 displays
-- as 3.0 and bands as Building; the two diverge at the boundary and the
-- band must follow the raw value.
ALTER TABLE overview_scores ADD COLUMN band band_t
  GENERATED ALWAYS AS (
    CASE WHEN composite IS NULL THEN NULL
         WHEN composite < 2.0   THEN 'Activating'
         WHEN composite < 3.0   THEN 'Building'
         WHEN composite < 4.0   THEN 'Competing'
         ELSE 'Differentiating' END) STORED;
```

One rule, two implementations, asserted equal
The database generates the band and the frontend resolver renders the colour. Two implementations of one rule is exactly the shape that produced a directory rendering every score in brand teal, so a test asserts they agree for every score in a fixture run rather than trusting that both were written from the same table.

## The page query

```
-- One resolution, then one select per section, issued concurrently.
-- No joins across sections: each is independently promoted and
-- independently absent.

WITH active AS (
  SELECT r.id AS run_id, r.entity_id, r.scored_cells, r.catalogue_cells,
         r.ccg_catalog_version, r.promoted_at, r.composite
    FROM runs r
    JOIN entities e ON e.id = r.entity_id

SELECT * FROM overview_firmographics WHERE run_id = (SELECT run_id FROM active);
-- … ten more for the Overview page
```

Concurrent single-table selects on an indexed key outperform one wide join and — more importantly — a section that failed to promote returns no row rather than nulling columns the serialiser then has to distinguish from a legitimately empty section.

## The evidence drawer

```
SELECT ei.*,
       -- bidirectional: the drawer renders chips that jump to the
       -- other cells this item backs, so a wrong link is visible
       -- from two directions
       array_agg(esl.subcap_id) AS supports_subcap_ids,
       (SELECT count(*) FROM evidence_run_links erl
         WHERE erl.e_id = ei.e_id) AS seen_in_runs
  FROM evidence_index ei
  LEFT JOIN evidence_subcap_links esl
         ON esl.e_id = ei.e_id AND esl.run_id = :run_id
 WHERE ei.e_id = :e_id
   AND ei.entity_id = :entity_id      ← the serving-side filter
 GROUP BY ei.e_id;
```

The entity predicate is load-bearing
Evidence dedup deliberately allows a cross-entity keep, because the same public document can legitimately be evidence for two institutions. That makes the serving-side filter the thing that stops one client's drawer opening another's row. It is not defensive coding; it is the mechanism.

## Coverage — over the run's own denominator

```
SELECT s.pillar_id,
       count(*)                                    AS cells_total,
       count(*) FILTER (WHERE s.linked > 0)        AS cells_covered,
       round(100.0 * count(*) FILTER (WHERE s.linked > 0)
                   / nullif(count(*), 0), 1)       AS pct
  FROM (
    SELECT sc.subcap_id, sc.pillar_id,
           (SELECT count(*) FROM evidence_subcap_links l
             JOIN evidence_index ei ON ei.e_id = l.e_id
            WHERE l.subcap_id = sc.subcap_id
              AND l.run_id    = sc.run_id
              AND ei.identity_ok) AS linked
      FROM subcap_scores sc WHERE sc.run_id = :run_id
  ) s
 GROUP BY s.pillar_id;
```

Three things this encodes. Coverage counts linked evidence only — an item resolving to no cell counts nowhere. An item failing the identity check counts nowhere either. And the denominator is the run's own scored cells, over the same cell set the heatmap serves, because a coverage figure computed over a different denominator is a contradiction a reader can find by counting.

## Retention of promoted staging rows

Promotion retains its inputs
Staging rows are marked promoted rather than deleted. That is what makes a single-page fix possible: a session re-claims a promoted run, resubmits one page, and promotion asserts a pass on every page — five from the retained rows, one from the new submission — then rewrites every serving table in one transaction. If promotion cleared its inputs, fixing one card would require re-synthesising every page.

## The index

```
-- HNSW, not IVFFlat. IVFFlat needs a training pass over a representative
-- sample and degrades as rows are inserted after training — and this table
-- grows one run at a time, indefinitely. HNSW is incremental and needs no
-- training, at the cost of a larger index and a slower build. The build
-- is created once at migration; the graph then grows incrementally as
-- each run's vectors are inserted at ingest, off the critical path.
CREATE INDEX bundle_emb_hnsw ON bundle_embeddings
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Every probe is run-scoped. This filter runs first, so the ANN search
-- happens over a few thousand rows rather than the whole corpus.
CREATE INDEX bundle_emb_run
  ON bundle_embeddings (run_id, scope_kind, scope_id);

-- Dimension guard. pgvector will not compare vectors of differing width,
-- but this fails at INSERT with a readable message rather than at query.
ALTER TABLE bundle_embeddings
  ADD CONSTRAINT emb_dim_384 CHECK (vector_dims(embedding) = 384);
```

## The check, in SQL

```
-- Similarity of a submitted field against its scope centroid.
-- <=> is cosine DISTANCE, so similarity is 1 minus it.
SELECT 1 - (c.centroid <=> :q) AS similarity, c.threshold, c.member_n
  FROM bundle_centroids c
 WHERE c.run_id = :run AND c.scope_kind = :scope
   AND c.scope_id IS NOT DISTINCT FROM :scope_id;

-- On a flag: what IS this text closest to? A bare number is not
-- actionable; three nearest chunks tell the agent what it drifted toward.
SET LOCAL hnsw.ef_search = 100;
SELECT source_kind, source_ref, left(content, 240) AS snippet,
       1 - (embedding <=> :q) AS similarity
  FROM bundle_embeddings
 WHERE run_id = :run AND scope_kind = :scope
   AND scope_id IS NOT DISTINCT FROM :scope_id
 ORDER BY embedding <=> :q
 LIMIT 3;
```

Scope | Threshold | Applies to

cell | 0.62 | A cell synthesis, which should be tightly about its own evidence

category | 0.58 | Focus areas and cell-group claims

pillar | 0.55 | Platform claims and pillar-level findings

run | 0.50 | The executive summary and framing sentence — legitimately synthetic

Thresholds tighten as the scope narrows, because a claim about one cell has less licence to roam than a document-level summary. They move like any other gate ceiling: only upward, and never loosened to make a submission pass.

Abstention is recorded, not silent. If the embedding tier is unavailable, if no centroid exists for the applicable scope, or if member_n is below five, V4 writes a NOT_RUN gate result with its reason. A gate that reports pass because it did not run is worse than one that reports fail.

## Why pgvector and not a separate store

Every query is run-scoped and joins back to relational rows — the evidence id, the source reference, the run. A dedicated vector database would mean a second system to keep consistent with the ingested tier, a second place a run can be half-deleted, and a network hop on the submit path. At roughly 4 to 7 million vectors and 10 to 20 GB across a 300-entity corpus, the scale does not demand it and the consistency cost is real.

Revisit past roughly 50M vectors, or if user-facing semantic search returns — and the second is a product decision, not an infrastructure one.

# Transactions and concurrency

One long transaction, two partial unique indexes and an advisory lock carry the whole concurrency model. Isolation stays at read committed because atomicity, not serialisability, is what this design needs.

## Why read committed is sufficient

The failure serialisable isolation protects against is a read that interleaves with a write and sees an inconsistent mixture. Here the only write that touches serving data is the promote, and it is one transaction across every table — so a concurrent reader sees the entire previous run or the entire new one, never a mixture. Raising the isolation level would add serialisation failures and retry logic to buy a guarantee already held.

## The promote transaction

```
BEGIN;  -- read committed

  -- 1. Serialise promotes of THIS run at the database, not only at the
  --    Redis lease. The lease is advisory and can expire mid-transaction;
  --    this cannot.
  SELECT id FROM runs WHERE id = :run FOR UPDATE;

  -- 2. Assert a PASS on every page. Otherwise 409, having written nothing.
  SELECT page FROM submissions
   WHERE run_id = :run AND superseded_at IS NULL AND status = 'PASS';

  -- 3. Deactivate the previous active run for this entity. A concurrent
  --    promote of a DIFFERENT run of the same entity violates the partial
  --    unique index and rolls back — which is the correct outcome.
  UPDATE runs SET is_active = FALSE, status = 'SUPERSEDED'
   WHERE entity_id = :entity AND is_active;

  -- 4. Run WRITERS[section] for each of the 34 sections: delete-then-insert
  --    per serving table, scoped to run_id.
  -- 5. Stamp promoted_at, producer_version and provenance on every row.
  -- 6. Mark the staging rows promoted — RETAINED, so a one-page fix can
  --    re-promote without re-synthesising the other five.

  UPDATE runs SET is_active = TRUE, status = 'PROMOTED', promoted_at = now()
   WHERE id = :run;

COMMIT;

-- AFTER commit, never inside: REFRESH ... CONCURRENTLY cannot run in a
-- transaction block, and it must not hold the promote open.
REFRESH MATERIALIZED VIEW CONCURRENTLY corpus_rollup;
```

## Lock inventory

Lock | Held by | Prevents

SELECT … FOR UPDATE on the run row | promote, for its duration | Two promotes of one run interleaving their writers

Partial unique on runs (entity_id) WHERE is_active | the index | Two active runs for one entity, however they arrive

Partial unique on submissions (run_id, page) WHERE superseded_at IS NULL | the index | Two live submissions for one page

Redis claim lease, with expiry | the synthesis session | Two Cowork sessions on one run. Advisory — expires so a dead session cannot block a run for ever

Row locks from delete-then-insert | promote, per serving table | Nothing a reader notices — readers take no locks under MVCC

Two layers, deliberately
The Redis lease is the ergonomic guard: it gives a second session a clean refusal rather than a database error. The row lock is the correctness guard: it holds even when the lease has expired mid-transaction. Neither alone is enough — the lease can lapse, and the row lock gives an unhelpful message.

## Lock ordering, and the deadlock that would otherwise happen

The promote touches 34 tables. Two promotes for different entities acquiring those tables in different orders would deadlock. The writer registry is therefore an ordered list, not a mapping, and every promote walks it in the same order.

```
# WRITERS is a list, and the order is load-bearing rather than cosmetic.
# A test asserts it is stable across imports, because a dict comprehension
# somewhere upstream reordering it would produce an intermittent deadlock
# that only appears under concurrent promotion.
WRITERS: list[tuple[str, Writer]] = [
    ("overview.scores",        write_overview_scores),
    ("overview.firmographics", write_overview_firmographics),
    ...                                  # 34 entries, fixed order
]
```

## What a reader sees during a promote

Moment | The reader sees

Before COMMIT | The entire previous run. The transaction is invisible.

At COMMIT | The entire new run, atomically.

Mid-writer failure | The entire previous run. Rollback leaves nothing behind.

Holding a pinned run id | The run they pinned, active or not, until they choose to move.

Between commit and the rollup refresh | Fresh page content beside a directory count up to a few seconds old — the one acceptable staleness window, and why the rollup carries no per-section figures.

## Retry policy

Failure | Retry | Because

Deadlock detected | Yes, up to 3 | Should not occur given ordered writers, but a retry is cheap and the alternative is a failed promote

Unique violation on the active-run index | No | Another run of this entity promoted first. Re-resolve rather than retry — retrying would deactivate their work

Lock timeout on the run row | Yes, with backoff | Another promote of the same run is in flight and will finish

Statement timeout mid-writer | No | A writer exceeding 300 seconds is a bug, not contention. Fail loudly.
